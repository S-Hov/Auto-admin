# План исправлений безопасности и подготовки Auto Admin к production

Этот документ — последовательный рабочий план. Выполнять разделы следует по порядку: более поздние шаги опираются на гарантии предыдущих.

## Общие правила работы

- Не объединять несколько крупных исправлений в один коммит.
- После каждого серверного шага запускать:

  ```bash
  docker compose exec -T server npx tsc --noEmit --skipLibCheck false
  ```

- После каждого клиентского шага запускать:

  ```bash
  docker compose exec -T client npx tsc -b --noEmit
  ```

- Миграции проверять только на чистой тестовой базе или после резервной копии.
- Не добавлять реальные токены, пароли и `.env` в Git.
- Не считать CORS средством авторизации: запросы можно отправлять без браузера.
- Не скрывать неизвестные серверные ошибки новым общим `ApiError`: исходная ошибка должна дойти до глобального `errorHandler` и попасть в серверный лог.

## Этап 1. Авторизация установочного API

### Проблема

Сейчас внешний клиент может участвовать в установке без подтверждения, что он является владельцем развёртывания. В установочное окно входят:

- подключение и сохранение конфигурации БД;
- применение миграций;
- создание первого администратора.

Транзакция не решает проблему захвата установки: она гарантирует одного администратора, но администратором станет тот, кто первым отправил запрос.

### Целевая модель

Владелец развёртывания задаёт секрет:

```env
Auto_Admin__INSTALL_TOKEN=<случайный токен длиной не менее 32 байт>
```

Рекомендуемая генерация:

```bash
openssl rand -hex 32
```

Клиент передаёт токен только в заголовке:

```http
X-Auto-Admin-Install-Token: <token>
```

Токен не передаётся в URL, query string или серверные логи.

### Серверные изменения

1. Добавить `Auto_Admin__INSTALL_TOKEN` в:

   - `server/.env.example` — только пример, без настоящего секрета;
   - `server/src/types/environment.d.ts`;
   - локальную конфигурацию Docker через внешнюю переменную, а не захардкоженное значение.

2. Создать middleware `server/src/shared/middleware/requireInstallToken.ts`.

3. Middleware должен:

   - проверить наличие серверного токена и его минимальную длину;
   - получить заголовок через `req.get('x-auto-admin-install-token')`;
   - вычислить SHA-256 обоих значений;
   - сравнить два Buffer через `crypto.timingSafeEqual()`;
   - одинаково отвечать на отсутствующий и неправильный токен;
   - возвращать `401` с кодом `INSTALL.INVALID_SETUP_TOKEN`;
   - при отсутствующей серверной конфигурации передавать внутреннюю ошибку в `errorHandler`.

4. Подключить middleware один раз в начале `installRouter`:

   ```text
   installRouter.use(requireInstallToken)
   ```

5. Защищены должны быть все маршруты `/api/install`, включая:

   - `POST /check-connection`;
   - `GET /migrations/plan`;
   - `POST /migrations/apply-next`;
   - `POST /auth/register`.

6. `GET /api/bootstrap/status` должен остаться публичным.

### Клиентские изменения

1. Добавить ввод setup token на установочную страницу.
2. Хранить токен только в React state/context текущей вкладки.
3. Не сохранять его постоянно в `localStorage`.
4. При перезагрузке страницы допустимо запросить токен повторно.
5. Добавлять заголовок только к install-запросам, а не ко всему API.
6. После стадии `ready` очистить токен из памяти клиента.

### Жизненный цикл токена

- Install API дополнительно продолжает проверять bootstrap/installation state.
- После `ready` установочные операции запрещены даже с правильным токеном.
- После успешной установки владелец должен удалить или заменить deployment token.
- Возврат в recovery-режим требует нового осознанного токена.

### Критерии готовности

- Без заголовка любой `/api/install/*` возвращает `401`.
- Неправильный токен возвращает такой же `401`.
- Правильный токен пропускает запрос к следующему middleware.
- Bootstrap работает без токена.
- Токен отсутствует в Git, URL, toast-сообщениях и логах.

## Этап 2. Укрепление подключения и сохранения конфигурации БД

### 2.1. Допустимые состояния

Обычный `/check-connection` разрешается только в `database_required`.

`database_unavailable` может означать временное падение уже работающей production-БД. Нельзя молча разрешать замену её конфигурации.

Для исправления недоступной существующей БД позднее создать отдельное действие recovery, которое:

- требует setup token;
- явно сообщает пользователю, что конфигурация будет заменена;
- требует дополнительного подтверждения;
- не вызывается автоматически обычной install-формой.

### 2.2. Runtime-валидация body

Создать Zod-схему для `check-connection` и подключить общий `validate(...)`.

Проверить:

- `host`: строка после `trim`, длина `1..255`;
- `port`: целое число `1..65535`;
- `database`: непустая строка с разумным ограничением длины;
- `user`: непустая строка с разумным ограничением длины;
- `password`: строка, пустой пароль допускается осознанно, максимальная длина ограничена;
- неизвестные поля либо удаляются схемой, либо отклоняются выбранной политикой.

TypeScript-интерфейс сам по себе входящий JSON не валидирует.

### 2.3. Ограничение соединения

В `checkConnection()` добавить:

- `connectTimeout`, например 5 секунд;
- единый тип строки результата `SELECT VERSION()` вместо `any`;
- гарантированное закрытие соединения;
- безопасное серверное логирование без пароля.

### 2.4. Разделение ошибок

Текущий широкий `catch` в `checkConnectionService` превращает в `400` не только отказ подключения, но и:

- ошибку записи `.env`;
- ошибку rename;
- ошибку прав файловой системы;
- ошибку сброса pool.

В `badRequest` преобразуется только ожидаемая ошибка проверки реквизитов. Файловые и внутренние ошибки должны дойти до `errorHandler` как `500` с исходным stack trace.

### 2.5. Конкурентная запись `.env`

Два одновременных запроса не должны использовать один и тот же временный путь и перетирать результат друг друга.

Варианты:

- сериализовать операцию server-side lock/mutex;
- использовать уникальный временный файл на запрос и атомарный rename;
- повторно проверить bootstrap state непосредственно перед сохранением.

### 2.6. SSRF и abuse protection

Подключение к произвольному MySQL-хосту является необходимой функцией self-hosted продукта, поэтому полностью запретить private IP нельзя. Защита строится на:

- обязательном setup token;
- rate limit для `/check-connection`;
- коротком connect timeout;
- ограничении размера JSON body;
- отсутствии подробных сетевых ошибок в ответе клиенту;
- опциональном allowlist хостов/CIDR для жёстких deployment-политик.

### Критерии готовности

- Невалидный port/host отклоняется до mysql2.
- В состоянии `ready`, `migrations_required` и `admin_required` смена БД запрещена.
- Обычный endpoint не заменяет конфигурацию при `database_unavailable`.
- Ошибка файловой системы возвращает безопасный `500` и логируется на сервере.
- Параллельные запросы не повреждают `.env`.

## Этап 3. Защита создания первого администратора

### Обязательные меры

1. Маршрут регистрации защищён setup token из этапа 1.
2. Сохраняется текущая транзакционная проверка `status = migrated` и блокировка `FOR UPDATE`.
3. Добавляется небольшой rate limit на регистрацию, например 5 запросов за 15 минут на IP/setup-сессию.
4. Минимальная длина пароля увеличивается как минимум до 12 символов. Ограничение максимальной длины остаётся для защиты от CPU abuse.
5. Стоимость bcrypt выбирается измерением на целевом сервере; запрос не должен надолго блокировать event loop.
6. Клиент и сервер используют одну смысловую политику пароля, но сервер остаётся источником истины.

### CPU DoS

`bcrypt.hash()` выполняется до транзакционной проверки. После setup token и rate limit это допустимо, но без них злоумышленник может массово запускать дорогое хеширование.

Не следует бездумно переносить bcrypt внутрь длинной транзакции: это увеличит время удержания DB-lock. Сначала закрыть маршрут токеном и limiter, затем измерить производительность.

### Критерии готовности

- Без setup token bcrypt не запускается.
- После `ready` endpoint не выполняет bcrypt и возвращает конфликт состояния.
- Два параллельных корректных запроса создают ровно одного администратора.
- Слабый пароль отклоняется Zod-схемой.

## Этап 4. Конкурентно-безопасный login rate limiter

### Что уже сделано правильно

Используются три области ограничения:

- пользователь со всех IP;
- IP по всем пользователям;
- конкретная пара пользователь + IP.

Это защищает от распределённого перебора аккаунта, password spraying и локального targeted brute force.

### Текущая проблема

Сейчас выполняются отдельные операции:

```text
SELECT counters
→ проверка в Node.js
→ bcrypt
→ INSERT failure
```

Несколько параллельных запросов могут одновременно прочитать старое значение и все пройти лимит.

### Целевая модель

Разделить две ответственности:

1. `login_attempts` — аудит неуспешных входов.
2. `auth_rate_limits` — атомарные счётчики/окна ограничения.

Перед bcrypt атомарно резервируется попытка. В распределённой системе источник истины должен находиться в MySQL или Redis, а не только в памяти одного Node.js процесса.

Возможная таблица счётчиков содержит:

- scope (`user`, `ip`, `user_ip`);
- нормализованный key или его hash;
- начало временного окна;
- count;
- updated_at;
- уникальный ключ `(scope, key, window_start)`.

Инкремент выполняется атомарным `INSERT ... ON DUPLICATE KEY UPDATE count = count + 1`. Проверка получает уже увеличенное значение.

### Дополнительный burst limiter

На HTTP-route нужен быстрый IP limiter, который останавливает большой burst до запросов к БД и bcrypt. Если приложение будет запущено в нескольких экземплярах, memory store недостаточен.

### IP за reverse proxy

Перед production deployment определить схему прокси:

- без прокси использовать socket address;
- за доверенным reverse proxy настроить точное количество trusted hops;
- не включать `app.set('trust proxy', true)` без понимания инфраструктуры, иначе клиент сможет подделывать IP через forwarded headers.

### Типы агрегатов MySQL

`SUM()` может возвращаться mysql2 как строка. Repository обязан явно преобразовать и проверить значения, а не обещать `number` только интерфейсом TypeScript.

### Индексы и retention

Добавить индекс:

```text
(username, created_at)
```

Текущий `(username, ip_address, created_at)` не оптимален для запроса только по username и времени.

Историю необходимо очищать или архивировать. Например, удалять записи старше 30–90 дней отдельной фоновой задачей. Не выполнять большую очистку в login-запросе.

### Ответ 429

- Возвращать стабильный error code.
- Добавлять `Retry-After`.
- Не раскрывать существование пользователя.
- Лимиты и длительности вынести в конфигурацию/константы.

### Обязательные тесты

- Последовательные неправильные пароли достигают лимита.
- 20 параллельных запросов не обходят лимит.
- Перебор одного username с разных IP ограничивается user scope.
- Перебор разных username с одного IP ограничивается IP scope.
- Успешный пароль не обходит уже действующую блокировку выбранной политики.
- Отсутствующий пользователь получает те же ответы, что существующий.

## Этап 5. Migration recovery

### Текущее безопасное поведение

- История строго проверяется по version/name/file/checksum.
- `failed` и `running` выбрасывают `MigrationRecoveryRequiredError`.
- Обычный runner не делает автоматический retry.
- Существующая запись истории не перезаписывается upsert-ом.
- В одном SQL-файле находится один statement.

Эти гарантии нельзя ослаблять.

### Bootstrap stage

Добавить stage:

```text
migration_recovery_required
```

Bootstrap должен распознавать только `MigrationRecoveryRequiredError`. Публичный bootstrap-ответ сообщает stage, но не возвращает SQL, checksum, путь файла или полный `error_message`.

Остальные неожиданные ошибки остаются `system_error`.

### Recovery API

Recovery API:

- защищён setup/recovery token;
- работает под migration lock;
- повторно загружает каталог и историю после получения lock;
- никогда не меняет checksum исходной попытки;
- требует version/checksum как optimistic precondition;
- записывает, кто и какое решение принял.

Допустимые явные решения:

1. `mark-applied` — только после проверки, что ожидаемое изменение схемы действительно существует.
2. `retry` — только после подтверждения, что прошлый statement не применился или безопасно повторяем.
3. ручное исправление — сервер остаётся заблокированным до повторной диагностики.

Для полноценного аудита лучше завести отдельную таблицу попыток/recovery events, а не перезаписывать одну строку history.

### Критерии готовности

- `failed/running` не появляются в обычном pending-плане.
- Bootstrap возвращает recovery-stage без технических деталей.
- Обычный `apply-next` заблокирован.
- Recovery-действие требует токен, lock и явное подтверждение версии/checksum.
- Повторная попытка не уничтожает сведения о предыдущей.

## Этап 6. Границы модулей и фасады

### Исправить именование

Файлы `auth.queries.ts` и `bootstrap.queries.ts` вызывают service, а не выполняют repository query. Переименовать их в `*.facade.ts` или экспортировать публичные функции через `index.ts`.

### Публичные типы

- Не экспортировать `ActiveSessionRow` наружу auth-модуля: это persistence-модель repository.
- Экспортировать DTO/service result, необходимые middleware.
- Использовать `import type` для type-only imports.
- Убрать лишние `return await`, если дополнительный stack/catch не нужен.

### Правило зависимостей

```text
shared middleware → публичный index модуля
module service → repository своего модуля
repository → db
```

Shared middleware не импортирует внутренний repository другого модуля.

## Этап 7. Production infrastructure

### 7.1. Конфигурация окружения

Создать централизованную Zod-валидацию env, но разделить переменные:

- обязательные для запуска HTTP-сервера;
- обязательные только для install authorization;
- DB-переменные, которые законно отсутствуют до первой настройки.

Нельзя делать fail-fast по отсутствующим DB credentials, иначе первая установка не запустится.

### 7.2. Graceful shutdown

- Сохранить результат `app.listen()`.
- Обработать `SIGTERM` и `SIGINT`.
- Перестать принимать новые соединения.
- Дать активным запросам ограниченное время.
- Закрыть DB pool.
- Не вызывать `process.exit()` до завершения cleanup, кроме аварийного таймаута.

### 7.3. CORS

- Вынести production origins в env.
- Не использовать CORS вместо authentication/authorization.
- Не разрешать произвольный origin с credentials.

### 7.4. Структурированное логирование

- Подключить Pino или другой JSON-логгер.
- Добавить request ID.
- Маскировать password, cookies, authorization и setup-token headers.
- Логировать stack неизвестных ошибок только на сервере.
- Не записывать полный request body установочных и auth-запросов.

### 7.5. Таймауты

Различать:

- connect timeout — время установления соединения;
- query timeout — время выполнения конкретного SQL;
- HTTP request timeout;
- graceful shutdown timeout.

Один `connectTimeout` не ограничивает долгий запрос.

### 7.6. Общие API-константы

- Создать каталог error codes через объект `as const`.
- Централизовать cookie options.
- Удалить неиспользуемый параметр `success` из `ApiError`, если он действительно нигде не нужен.

## Этап 8. Тестирование перед production

### Install flow

- Bootstrap без DB config.
- Неправильный и правильный setup token.
- Невалидные DB credentials и timeout.
- Успешное сохранение `.env`.
- Строгий порядок миграций.
- Конфликт устаревшей expectedVersion.
- Два параллельных apply-next.
- Создание ровно одного администратора.
- Запрет всех install mutations после `ready`.

### Migration integrity

- Изменённый checksum блокирует запуск.
- Переименованный файл блокирует запуск.
- Неизвестная запись history блокирует запуск.
- `failed` и `running` приводят к recovery-stage.
- SQL-файлы присутствуют в production `dist`.

### Authentication

- Login/logout/getMe.
- Неактивный пользователь не получает сессию.
- Истёкшая и отозванная сессии отклоняются.
- Последовательный и параллельный brute force.
- IP/user/user+IP scopes.
- Корректный IP за доверенным proxy.
- Cleanup старых login attempts.

### Security regression

- Реальные `.env` и токены отсутствуют в Git.
- Setup token не появляется в логах.
- `npm audit --omit=dev` для клиента и сервера.
- Ограничен JSON body size.
- Неизвестная ошибка возвращает безопасный `500` без stack trace клиенту.
