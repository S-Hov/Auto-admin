# Редактор структуры меню

Статус: архитектурный план для ветки `S-Hov/menu-editor`. Документ описывает целевое поведение редактора, клиентское состояние и необходимые изменения серверного API. Это не описание уже полностью реализованной функциональности.

## 1. Задача

После чистой установки таблица `Auto_Admin__menu` пуста. Пользователь не должен зависеть от тестового mock-меню: системный администратор должен иметь возможность создать структуру навигации из интерфейса, изменить её и сразу увидеть результат в каждом поддерживаемом варианте меню.

Редактор должен позволять:

1. увидеть пункты в виде дерева;
2. создать корневой или дочерний пункт;
3. изменить название, `slug`, иконку и активность;
4. перенести пункт к другому родителю;
5. изменить порядок пунктов среди соседей;
6. удалить пункт без детей;
7. посмотреть текущую структуру в вариантах `sidebar`, `gooey` и `topbar`;
8. не потерять подтверждённые изменения после перезагрузки страницы;
9. в дальнейшем настроить права ролей и пользователей на пункт.

Редактор управляет **структурой навигации**, а не правами доступа к данным. Права `canView/canCreate/canUpdate/canDelete` у меню не дают доступа к таблицам через Query API.

## 2. Принятые решения

### 2.1. Отдельная страница

Редактор располагается по адресу:

```text
/:locale/settings/menu
```

Он не открывается в модальном окне: доске нужны полноценная рабочая область, панель свойств и живой предпросмотр.

Маршрут редактора не должен зависеть от содержимого динамического меню. Если таблица меню пуста, администратор всё равно попадает на страницу по прямой ссылке или через постоянную системную кнопку настройки.

Фронтенд скрывает ссылку от обычного пользователя для удобства, но это не защита. Каждый управляющий endpoint на сервере самостоятельно требует системного администратора.

### 2.2. Сервер остаётся источником истины

Нет общей кнопки «Сохранить всё дерево». Сервер сохраняет каждую завершённую смысловую операцию:

- создание пункта после отправки заполненной формы;
- сохранение панели свойств;
- переключение активности;
- отпускание перетаскиваемого пункта в новом месте;
- подтверждённое удаление;
- изменение прав.

Панорамирование, масштабирование, выбор узла, ввод незавершённого текста и движения указателя во время drag-and-drop запросов не создают.

Клиент применяет операцию оптимистично, показывает `Сохранение…`, а при ошибке откатывает её или заменяет состояние свежим ответом сервера. Это даёт быстрый интерфейс без большого несохранённого черновика.

### 2.3. Плоский список — каноническая клиентская модель

Сервер возвращает плоский `MenuItem[]`. На клиенте из него вычисляются дерево, граф доски и данные предпросмотра.

Не следует хранить независимые изменяемые копии плоского списка и дерева: после переноса они могут рассинхронизироваться. Дерево всегда является производным значением.

### 2.4. Положение узла означает структуру

Свободные координаты `x/y` не сохраняются в БД. Раскладка дерева строится автоматически по `parentId` и порядку соседей.

Перетаскивание узла означает одно из двух действий:

- изменение родителя;
- изменение порядка среди детей одного родителя.

Перемещение камеры и масштаб — только состояние интерфейса. Его можно позднее сохранять в `localStorage`, но не в `Auto_Admin__menu`.

## 3. Устройство страницы

```text
┌───────────────────────────────────────────────────────────────────┐
│ Назад │ Редактор меню │ Сохранено │ Поиск │ Fit │ − 100% + │ Вид  │
├──────────────────┬─────────────────────────────┬──────────────────┤
│                  │                             │                  │
│ Живой            │            Доска            │ Свойства пункта  │
│ предпросмотр     │                             │                  │
│                  │      дерево и связи         │ Основное         │
│ sidebar / gooey  │                             │ Доступ (позже)   │
│ / topbar         │                             │                  │
│                  │                             │                  │
└──────────────────┴─────────────────────────────┴──────────────────┘
```

### 3.1. Верхняя панель

Содержит:

- возврат к предыдущей странице;
- состояние синхронизации: `Сохранено`, `Сохранение…`, `Ошибка сохранения`;
- поиск пункта по названию или `slug`;
- уменьшение и увеличение масштаба;
- `100%`;
- `Fit to screen`;
- выбор варианта предпросмотра;
- флаг показа/скрытия предпросмотра.

### 3.2. Доска

Дерево по умолчанию располагается слева направо: каждый уровень вложенности образует следующий столбец.

Узел отображает:

- круглую область с иконкой;
- название под ней;
- состояние активности;
- выделение выбранного и сохраняемого узла;
- кнопку добавления ребёнка при наведении;
- контекстные действия редактирования и удаления.

Связи между узлами показывают отношение родитель → ребёнок. Неактивный пункт остаётся видимым в редакторе, но визуально приглушается.

Поиск выделяет найденный узел и перемещает камеру к нему.

### 3.3. Виртуальный корень

На доске всегда существует виртуальный узел `Меню`. Он не имеет серверного ID и не сохраняется в БД.

Его дети — пункты с `parentId: null`. Кнопка добавления возле виртуального корня создаёт корневой пункт. Благодаря этому пустое меню не является особым вариантом дерева.

### 3.4. Панель свойств

При выборе сохранённого узла панель показывает:

- `name`;
- `slug`;
- `iconType`;
- `icon`;
- `isActive`;
- родителя и позицию только для чтения или как отдельное структурное управление;
- удаление.

Поля формы изменяются локально. Запрос обновления отправляется после нажатия кнопки сохранения, а не на каждый символ.

Нажатие на плюс открывает ту же панель в режиме создания. Пустая строка в БД не создаётся, пока форма не прошла валидацию и не была отправлена.

Удаление узла с детьми в первой версии запрещено. Интерфейс заранее блокирует кнопку и объясняет, что сначала надо удалить или перенести дочерние пункты. Сервер повторяет эту проверку.

### 3.5. Живой предпросмотр

Предпросмотр получает текущее оптимистичное состояние редактора, поэтому изменение видно сразу, до завершения запроса.

Он использует существующий реестр `AdminShellVariants`, но не должен содержать копии реализаций меню. Общие компоненты отображения необходимо переиспользовать или выделить из layout-компонентов.

В режиме предпросмотра:

- клики не выполняют реальную навигацию;
- пункт можно выделить на доске;
- отображение не делает собственный запрос к `/api/menu`;
- все пункты показываются как администратору;
- переключение `sidebar/gooey/topbar` является локальным состоянием редактора.

Сохранение выбранного варианта меню как настройки приложения — отдельная возможность. Оно не относится к структуре `Auto_Admin__menu` и не должно случайно выполняться только из-за переключения предпросмотра.

## 4. Контракты данных фронтенда

Ответы пользовательского и управляющего меню имеют разную структуру, поэтому им нужны разные схемы и типы.

### 4.1. Управляемый пункт

`GET /api/menu/manage` возвращает структуру без вычисленных прав:

```ts
interface ManageableMenuItemDto {
    id: number;
    parentId: number | null;
    name: string;
    slug: string;
    icon: string | null;
    iconType: "icon" | "svg" | "image" | "video";
    sortOrder: number;
    isActive: boolean;
}
```

### 4.2. Видимый пункт

`GET /api/menu` возвращает тот же пункт с эффективными правами текущего пользователя:

```ts
interface VisibleMenuItemDto extends ManageableMenuItemDto {
    canView: boolean;
    canCreate: boolean;
    canUpdate: boolean;
    canDelete: boolean;
}
```

Существующий клиентский `MenuItemDto`, всегда требующий `can*`, нельзя использовать для `/manage` без исправления контракта.

### 4.3. Состояние редактора

Минимальное состояние страницы:

```text
loadState       loading | ready | error
items           ManageableMenuItemDto[]
selectedId      number | virtual-root | null
editorMode      view | create | edit
syncState       idle | saving | error
pendingCommand  текущая серверная команда или null
previewVisible  boolean
previewVariant  sidebar | gooey | topbar
search          string
viewport        масштаб и положение камеры
```

Структурные мутации выполняются последовательно. Пока перенос сохраняется, следующий перенос либо блокируется, либо помещается в явную очередь. Нельзя допустить, чтобы ответы двух запросов пришли в обратном порядке и заменили новое дерево старым.

## 5. Целевой HTTP API

Все маршруты требуют действующей сессии. Управляющие маршруты требуют системного администратора и повторно проверяют его статус в БД внутри транзакции, как уже делает `MenuService.manage()`.

### 5.1. Получение данных

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/menu` | Эффективное меню текущего пользователя |
| `GET` | `/api/menu/manage` | Полное дерево для редактора |

Пустой массив от `/manage` — успешное состояние, а не ошибка.

### 5.2. Создание

```text
POST /api/menu
```

```json
{
  "parentId": null,
  "beforeId": null,
  "name": "Заказы",
  "slug": "orders",
  "icon": "basket-cart-classic",
  "iconType": "icon",
  "isActive": true
}
```

`beforeId: null` означает добавление в конец детей выбранного родителя. Клиент не назначает окончательный `sortOrder`: сервер рассчитывает его по текущему дереву.

### 5.3. Изменение свойств

```text
PATCH /api/menu/:id
```

```json
{
  "name": "Все заказы",
  "slug": "all-orders",
  "icon": "menu-bullet-list",
  "iconType": "icon",
  "isActive": true
}
```

Этот endpoint не меняет `parentId` и порядок. Разделение не позволяет обычной форме свойств случайно изменить структуру.

Текущий сервер использует `POST /api/menu` с необязательным `id` и принимает `sortOrder`. До подключения редактора контракт следует разделить на создание, изменение свойств и позиционирование.

### 5.4. Перемещение и сортировка

```text
PUT /api/menu/:id/position
```

```json
{
  "parentId": 7,
  "beforeId": 10
}
```

Смысл: сделать пункт ребёнком `7` и поставить непосредственно перед пунктом `10`.

- `parentId: null` перемещает пункт на корневой уровень;
- `beforeId: null` помещает его последним среди детей нового родителя;
- `beforeId` должен быть ребёнком указанного `parentId`;
- `beforeId` не может совпадать с перемещаемым ID;
- пункт нельзя переместить внутрь самого себя или собственного потомка.

Клиент сообщает намерение, а сервер пересчитывает `sortOrder` затронутых соседей, например с шагом `10`.

### 5.5. Удаление

```text
DELETE /api/menu/:id
```

Удаляется только существующий листовой пункт. Каскадное удаление поддерева через публичный API первой версии не поддерживается.

### 5.6. Права пункта

Существующий маршрут сохраняется:

```text
PUT /api/menu/permissions
```

Редактор прав является отдельным подэтапом. Для него дополнительно понадобится управляющее чтение явных правил выбранной роли или пользователя; `GET /api/menu` текущего пользователя для этого недостаточно.

### 5.7. Ответ после мутации

После структурной мутации сервер должен вернуть каноническое дерево или данные, достаточные для его однозначного обновления. Для первой реализации проще возвращать полный `ManageableMenuItemDto[]`: лимит меню равен 500 пунктам, а единый ответ исключает рассинхронизация `sortOrder` соседей.

Клиент заменяет локальный подтверждённый снимок серверным ответом. Если запрос не удался, он откатывает оптимистичную операцию к предыдущему снимку.

## 6. Серверное выполнение команд

### 6.1. Общие правила

Каждая мутация выполняется в одной транзакции:

1. проверить principal как системного администратора;
2. повторно проверить активного администратора в БД с блокировкой;
3. прочитать дерево через `readAll(true)`;
4. проверить лимит, ID, уникальность `slug`, родителя и циклы;
5. применить изменение;
6. записать аудит;
7. вернуть каноническое дерево;
8. зафиксировать транзакцию.

Если изменение или аудит завершились ошибкой, вся операция откатывается.

### 6.2. Перемещение

Алгоритм позиционирования:

1. найти перемещаемый узел;
2. найти нового родителя, если он указан;
3. пройти цепочку родителей вверх и запретить цикл;
4. проверить `beforeId` и его принадлежность новому родителю;
5. убрать узел из списка старых соседей;
6. вставить его в нужное место новых соседей;
7. перенумеровать старую и новую группы с шагом `10`;
8. обновить только реально изменившиеся строки;
9. записать аудит действия как `update`, сохранив старые и новые `parentId/sortOrder`.

Если старый и новый родитель совпадают, перенумеровывается одна группа.

### 6.3. Конкурентное редактирование

Первая версия не требует WebSocket и совместного редактирования в реальном времени. Транзакционная блокировка защищает целостность одной команды.

Если команда ссылается на уже удалённый или перемещённый `beforeId`, сервер возвращает конфликт, а клиент перезагружает `/api/menu/manage` и сообщает, что дерево было изменено в другом окне.

Глобальную ревизию дерева или optimistic locking можно добавить позднее, если одновременное редактирование станет реальным сценарием.

## 7. Валидация

Клиентская Zod-схема нужна для формы и проверки ответа API, но серверная схема остаётся обязательной.

Сервер проверяет:

- положительные безопасные ID;
- `parentId` и `beforeId`;
- `name` после `trim`, длина 1–100;
- уникальный `slug` и его текущий формат;
- тип и безопасное значение иконки;
- булевый `isActive`;
- существование родителя;
- отсутствие циклов;
- отсутствие неизвестных полей в теле;
- лимит 500 пунктов;
- запрет удаления родителя с детьми.

Фронтенд повторяет пользовательские проверки для быстрого сообщения, но не пытается заменить ими сервер.

## 8. Ошибки и восстановление интерфейса

### Загрузка дерева не удалась

Показать состояние ошибки и кнопку повторной загрузки. Не подменять ошибку mock-данными.

### Меню пустое

Показать виртуальный корень, объяснение и действие «Создать первый пункт».

### Ошибка создания или изменения формы

Оставить введённые данные в панели, показать серверную ошибку и позволить повторить отправку.

### Ошибка перемещения

Вернуть предыдущий снимок дерева. При конфликте дополнительно загрузить актуальное дерево с сервера.

### Потеря соединения

Не показывать состояние `Сохранено`. Сохранить форму в памяти страницы и предложить повторить действие.

Mock-меню разрешено использовать в Storybook, тестах и изолированной демонстрации, но не как fallback рабочего API.

## 9. Границы первой версии

В первую версию входят:

- отдельная страница редактора;
- загрузка настоящего `/api/menu/manage`;
- пустое состояние;
- виртуальный корень;
- дерево на доске;
- pan/zoom/fit;
- создание и редактирование;
- изменение активности;
- удаление листа;
- reparent и сортировка;
- оптимистичный интерфейс с откатом;
- живой предпросмотр трёх существующих вариантов.

Не входят в первый подэтап:

- совместное редактирование в реальном времени;
- произвольные сохраняемые координаты узлов;
- каскадное удаление поддерева;
- undo/redo нескольких уже сохранённых серверных операций;
- импорт и экспорт меню;
- AI-редактирование;
- настройка прав ролей и пользователей внутри той же поставки;
- сохранение выбранного варианта shell как глобальной настройки.

## 10. Предлагаемая структура фронтенда

Имена можно уточнять при реализации, но ответственность должна оставаться разделённой:

```text
client/src/
  pages/menu-editor/
    ui/MenuEditorPage.tsx

  features/menu-editor/
    api/
      menu-editor.api.ts
      menu-editor.schema.ts
      menu-editor.types.ts
    model/
      menu-editor.reducer.ts
      menu-editor.selectors.ts
      menu-editor.commands.ts
      build-editor-tree.ts
    ui/
      MenuEditorToolbar.tsx
      MenuEditorBoard.tsx
      MenuEditorNode.tsx

      MenuPreviewPanel.tsx

```

API-контракты, которые используются не только редактором, могут остаться в `shared/api/menu`. Логика конкретной страницы и её оптимистичные команды принадлежат feature.

## 11. Порядок реализации

### Этап 1. Контракты фронтенда и настоящий GET

1. Разделить `ManageableMenuItemDto` и `VisibleMenuItemDto`.
2. Добавить отдельные Zod-схемы ответов `/api/menu` и `/api/menu/manage`.
3. Заменить mock внутри рабочего `getMenu()` настоящим API-вызовом.
4. Добавить `getManageableMenu()`.
5. Проверить пустой массив, ошибку контракта и нормальный ответ.

### Этап 2. Страница и статическая доска

1. Добавить маршрут `/:locale/settings/menu`.
2. Сделать состояния loading/error/empty/ready.
3. Построить виртуальный корень и дерево.
4. Реализовать выбор узла, pan/zoom/fit и автоматическую раскладку.
5. Пока не выполнять мутации.

### Этап 3. Серверные команды

1. Разделить схемы создания и изменения свойств.
2. Добавить `PATCH /api/menu/:id`.
3. Добавить `PUT /api/menu/:id/position`.
4. Перенести окончательный расчёт `sortOrder` на сервер.
5. Возвращать каноническое дерево после мутации.
6. Сохранить существующие транзакции, повторную проверку администратора и аудит.

### Этап 4. Формы и оптимистичные операции

1. Создание корневого и дочернего пункта.
2. Обновление свойств.
3. Немедленное переключение активности.
4. Удаление листового пункта.
5. Reparent и сортировка после drop.
6. Индикатор синхронизации, откат и повтор.

### Этап 5. Предпросмотр

1. Выделить переиспользуемое отображение меню из layout-компонентов, если необходимо.
2. Передавать в preview текущее состояние редактора.
3. Отключить настоящую навигацию.
4. Добавить переключение трёх вариантов и сворачивание панели.

### Этап 6. Права меню

1. Спроектировать чтение явных правил выбранного субъекта.
2. Добавить выбор роли или пользователя.
3. Отображать наследование отдельно от явного правила.
4. Использовать существующую запись через `/api/menu/permissions`.
5. Не смешивать эти флаги с правом открыть сам редактор.

## 12. Критерии готовности

Первую версию можно считать готовой, когда:

- администратор открывает редактор при пустой таблице;
- создаёт первый корневой пункт и ребёнка;
- после перезагрузки они остаются на месте;
- может изменить свойства и активность;
- может переставить пункт и изменить родителя без появления цикла;
- ошибка сервера не оставляет ложное состояние `Сохранено`;
- удалить родителя с детьми невозможно и на клиенте, и на сервере;
- все три предпросмотра используют одно текущее дерево;
- рабочий клиент не подменяет пустой или ошибочный API mock-данными;
- обычный пользователь не может изменить меню прямым HTTP-запросом;
- каждое подтверждённое изменение и аудит сохраняются атомарно.
