# Реализованный слой прав и Query API

Состояние на 1 октября 2026 года. Этот документ описывает рабочий серверный код из `access-control-architecture.md`: анализ запросов, вычисление прав, исполнение запросов, каталог доступного, изменение правил и меню. Конструктор страниц и его клиентский интерфейс относятся к следующему этапу.

## Что подготовить в своей базе

1. Применить миграции через существующий установщик. Добавлены `0023__Auto_Admin__menu_audit_events.sql` и `0024__Auto_Admin__menu_unique_slug.sql`. Старые миграции не переписывались. Если в меню уже есть одинаковые `slug`, их надо привести к уникальным значениям перед `0024`.
2. Войти системным администратором. Его роль должна иметь одновременно `key = admin` и `rights = full`.
3. Выполнить `POST /api/access/scan`. Сканирование создаст или обновит каталог пользовательских таблиц и полей. До первого успешного сканирования Query API возвращает `409 SCHEMA.CATALOG_REQUIRED`.
4. Получить `GET /api/access/catalog`. Администратор увидит пользовательские ресурсы; другие пользователи получат только разрешённые ресурсы, поля и действия.

Пользовательская база при реализации не изменялась. Проверки MySQL выполнялись в отдельном временном экземпляре с временными базами.

## Как запрос доходит до SQL

```text
HTTP JSON с version: 1
  → requireAuth: действующая сессия и активный пользователь
  → проверка версии и формы JSON
  → согласованный снимок сохранённого каталога и свежие правила из БД
  → анализ всех таблиц, полей и действий
  → проверка эффективных прав
  → нормализованный запрос с явными полями и LIMIT
  → компилятор провайдера
  → драйвер БД
  → ограничение размера результата
```

Полномочия берутся из сессии. В теле запроса нет разрешённых `principal`, `connection`, `skipAuthorization` и SQL-фрагментов. Ошибка загрузки правил останавливает выполнение, в том числе для администратора. Наружу возвращается безопасный код; причины отказа и ID целей пишутся в серверный журнал без значений из запроса.

Каталог для авторизации читается из служебной БД в отдельной транзакции: успешное сканирование из другого процесса будет видно следующему запросу. Правила читаются одним SQL statement без кеша. Набор прав фиксируется на время одной операции или последовательности: изменения начинают действовать со следующего запроса, уже исполняющаяся операция не отменяется автоматически.

Внешний DDL сам по себе не запускает сканирование. После изменения структуры пользовательской базы надо пересканировать её. Объекты, которые каталог уже считает отсутствующими, отклоняются до SQL; ещё не обнаруженное внешнее изменение может привести к ошибке БД. Успешного обхода прав через такой случай нет.

## Основные файлы

| Файл в `server/src` | Задача |
|---|---|
| `core/query-engine/schema/query.schema.ts` | Проверяет форму запросов, размеры, вложенность, операции, условия и pipeline |
| `core/query-engine/access/query-access.analyzer.ts` | Однозначно сопоставляет имена с каталогом, разворачивает `*`, собирает потребности в правах |
| `core/access-control/policy/permission.evaluator.ts` | Единые правила наследования роли, пользователя и поля |
| `core/access-control/access-control.service.ts` | Готовит контекст прав, разрешает запрос и строит каталог доступного |
| `core/query-engine/access/query-authorizer.ts` | Соединяет валидацию, анализатор и проверку прав |
| `core/query-engine/query-engine.service.ts` | Обязательная проверка для одиночного запроса и массива |
| `core/query-engine/pipeline/pipeline.executor.ts` | Проверяет все шаги до исполнения и повторно проверяет запрос после подстановки значений |
| `core/query-engine/pipeline/pipeline.references.ts` | Проверяет ссылки на предыдущие шаги и их порядок |
| `core/access-control/permission-management.service.ts` | Меняет правило вместе с аудитом, проверяет действующего администратора |
| `modules/menu/menu.service.ts` | Управляет деревом меню, видимостью и отдельными правами навигации |
| `modules/query`, `modules/access-control`, `modules/menu` | HTTP-маршруты и контроллеры |

Из серверного кода одиночный запрос выполняется через `queryEngineService.execute(query, principal)`. Для массива передаётся массив первым аргументом. Pipeline выполняется через `executePipeline(definition, principal)`. `principal` обязателен. Самостоятельно созданный `PipelineExecutor` тоже выполняет проверку прав.

Установщик, аутентификация, сканер схемы и управление служебными таблицами используют свои узкие репозитории с `DatabaseExecutor`. Они не отправляют служебный SQL в общий клиентский Query API. Универсального флага обхода прав нет.

## Query API версии 1

Все перечисленные маршруты требуют завершённой установки и действующей сессии. Ответы используют существующий формат `success/code/data`; успешные операции возвращают `COMMON.OK`.

### Одиночный запрос

`POST /api/query/execute`:

```json
{
  "version": 1,
  "query": {
    "action": "read",
    "table": "orders",
    "select": ["id", "total"],
    "where": {"total": {"_gt": 0}},
    "sort": [{"field": "id", "direction": "desc"}],
    "limit": 50
  }
}
```

Вместо объекта в `query` можно передать массив из 1–20 запросов. Сервер проверит весь массив прежде, чем начнёт транзакцию. Все изменения откатятся при ошибке SQL или превышении общего размера результата.

### JOIN

```json
{
  "version": 1,
  "query": {
    "action": "read",
    "table": "orders",
    "select": ["orders.total", "customer.name"],
    "joins": [{
      "table": "customers",
      "alias": "customer",
      "type": "LEFT",
      "on": {"orders.customer_id": "customer.id"}
    }]
  }
}
```

Поля с одинаковыми именами в нескольких таблицах надо квалифицировать. После назначения алиаса используем именно алиас. В `JOIN.on` и ключ, и значение — ссылки на поля, а не текст SQL или значение для сравнения.

Для `SELECT`, `WHERE`, `sort` и обеих сторон `JOIN` нужно право `read` на поле и его ресурс. Для записи нужно `create/update` на все записываемые поля. Удаление требует `delete` на ресурс и `read` на поля условия. Нет разрешения хотя бы на одну потребность — весь запрос получает `403 ACCESS.QUERY_DENIED`; запрещённые данные не заменяются пустым успешным ответом.

`select: ["*"]` и `select: ["customer.*"]` разворачиваются в явные колонки. Если среди них есть запрещённая, запрос отклоняется. Каталог доступного помогает клиенту заранее собрать разрешённый список.

### Pipeline

`POST /api/query/pipeline`:

```json
{
  "version": 1,
  "pipeline": {
    "transactional": true,
    "steps": [
      {
        "id": "created",
        "query": {"action": "create", "table": "orders", "data": {"total": 100}}
      },
      {
        "id": "loaded",
        "dependsOn": ["created"],
        "query": {
          "action": "read",
          "table": "orders",
          "select": ["id", "total"],
          "where": {"id": {"_eq": "$steps.created.insertId"}}
        }
      }
    ]
  }
}
```

Все шаги анализируются и авторизуются заранее. Ссылки допустимы только внутри значений `data` и `where`, только на предыдущий шаг. Поддерживаются `$steps.ID.insertId`, `$steps.ID.affectedRows`, `$steps.ID.rows.0.FIELD`. После подстановки сервер повторно проверяет форму и права. Отсутствующая ссылка или неподходящий тип значения приводит к ошибке, а не к незаметной подстановке `undefined`.

`transactional` по умолчанию равен `true`. Отключить транзакцию можно для pipeline, состоящего только из чтений. MySQL допускает транзакционные записи только в InnoDB; проверка этой возможности принадлежит провайдеру БД. MyISAM нельзя объявить безопасным для отката.

## Каталог и изменение прав

| Метод и путь | Доступ | Действие |
|---|---|---|
| `GET /api/access/catalog` | Любой авторизованный пользователь | Эффективные ресурсы, поля и действия |
| `POST /api/access/scan` | Системный администратор | Пересканирование схемы |
| `GET /api/access/permissions/role/2` | Системный администратор | Явные правила роли 2 |
| `GET /api/access/permissions/user/5` | Системный администратор | Явные правила пользователя 5 |
| `PUT /api/access/permissions` | Системный администратор | Создание, замена или удаление одного правила |

Пример изменения правила:

```json
{
  "subjectType": "role",
  "subjectId": 2,
  "targetType": "resource",
  "targetId": 15,
  "action": "read",
  "effect": "allow"
}
```

`targetId` — ID из служебного каталога, а не имя таблицы. Для поля используем `targetType: "field"`. У поля нет действия `delete`. `effect: null` удаляет явное правило и возвращает наследование. Правило пользователя переопределяет правило роли. Разрешение на поле не открывает запрещённый ресурс.

Администратор повторно проверяется в БД внутри транзакции с блокировкой его пользователя и роли. Проверяются субъект, существование и состояние цели, запрет служебных объектов и записи в view. Изменение правила и аудит сохраняются атомарно; повтор того же значения не создаёт лишнее событие. Кеш прав отсутствует.

Этот API не изменяет `roles.key`, `roles.rights`, `users.role_id` и `users.is_active` и не удаляет пользователей. Поэтому через него невозможно снять полномочия последнего системного администратора: правила данных не ограничивают его административный статус. Когда появится API управления пользователями и ролями, проверку количества оставшихся активных администраторов надо добавить непосредственно в его транзакцию.

## Меню

| Метод и путь | Доступ | Действие |
|---|---|---|
| `GET /api/menu` | Авторизованный пользователь | Доступная навигация |
| `GET /api/menu/manage` | Системный администратор | Всё дерево для редактора |
| `POST /api/menu` | Системный администратор | Создать пункт; с `id` — обновить |
| `DELETE /api/menu/:id` | Системный администратор | Удалить пункт без детей |
| `PUT /api/menu/permissions` | Системный администратор | Изменить права навигации роли/пользователя |

Тело создания/обновления:

```json
{
  "parentId": null,
  "name": "Заказы",
  "slug": "orders",
  "icon": "content-article",
  "iconType": "icon",
  "sortOrder": 0,
  "isActive": true
}
```

Пункт имеет уникальный `slug`. Сервер запрещает циклы, неизвестного родителя, удаление пункта с детьми и превышение 500 пунктов. Для обычной иконки передаём ключ каталога. SVG/изображение/видео задаются безопасным HTTPS URL или путём `/assets/...`; сырой SVG/HTML в этом API не принимается. На фронтенде SVG URL должен использоваться как изображение, а не вставляться через `innerHTML`.

Права меню:

```json
{
  "menuId": 1,
  "subjectType": "role",
  "subjectId": 2,
  "permissions": {
    "canView": true,
    "canCreate": false,
    "canUpdate": false,
    "canDelete": false
  }
}
```

`permissions: null` убирает явное правило. Существующее пользовательское правило переопределяет все четыре флага роли; отсутствие правил означает отказ. Дети скрытого или неактивного родителя тоже скрываются. Эти флаги относятся к навигации и её действиям: они не разрешают SQL и не дают возможность редактировать само меню неадминистратору.

Изменения пунктов и их прав записываются в `Auto_Admin__menu_audit_events` в той же транзакции. История остаётся после удаления пункта. Привязка к JSON страницы и построение разрешённой конфигурации страницы будут реализованы на следующем этапе.

## Ограничения первой версии

- 20 команд в массиве или pipeline, до 5 JOIN, до 100 полей/элементов в ограниченных списках, глубина JSON до 16 и до 2 000 узлов на запрос.
- `read` требует явный непустой `select`. По умолчанию возвращается до 100 строк; максимум — 500. Общий результат операции ограничен 2 MiB. Большой результат отклоняется, а не обрезается.
- Ограничение объёма применяется после получения результата драйвером. Это не потоковое чтение и не ограничение памяти MySQL. Ограничение строк, время запроса и ограничение частоты продолжают действовать отдельно.
- `update/delete` требуют непустые условия, включая вложенные логические операторы. Это не ограничение доступа к отдельным строкам; авторизованный пользователь всё ещё может задать условие, подходящее многим строкам.
- Для JOIN нельзя выбрать две разные колонки с одинаковым выходным именем, например `orders.id` и `customers.id`: объект строки mysql2 потерял бы одно значение. Такой запрос отклоняется. Явные выходные алиасы — последующее расширение JSON-контракта.
- Имена с точкой, обратной кавычкой или NUL в физических именах схемы/таблицы/поля не поддерживаются этим контрактом. Точки обозначают квалификацию.
- Генерируемые колонки доступны только для чтения. `returning`, `aggregate` и `OUTER JOIN` отклоняются, потому что текущий MySQL-компилятор их не реализует. Типы с заделом на эти возможности не означают их поддержку в публичном API.
- Правила строк (`только свои заказы`), выходные алиасы, JSON/BLOB-значения для записи и новые провайдеры СУБД потребуют отдельных расширений.

## Проверки

Vitest проверяет наследование прав, алиасы/неоднозначность, вложенные фильтры, обе стороны JOIN, wildcard, запись, служебные объекты, отсутствие сессии, обязательность principal, отзыв прав, отказы до SQL, ошибки pipeline, размеры ответа, аудит и дерево меню. HTTP-проверки используют настоящий Express с подменой сервисов для проверки границы сессии и формата ответа.

`npm test` в `server` запускает обычный набор. `npm run test:integration` запускает MySQL-проверки при `Auto_Admin__RUN_MYSQL_TESTS=1`. Нужны отдельные `Auto_Admin__TEST_DB_HOST`, `Auto_Admin__TEST_DB_PORT`, `Auto_Admin__TEST_DB_USERNAME`, `Auto_Admin__TEST_DB_PASSWORD`. Пользователь тестовой БД должен иметь право создавать и удалять временные базы. Тесты создают базы со случайными именами и удаляют их после проверки.

Интеграционная проверка применяет все миграции на чистой MySQL, проверяет внешние/уникальные ключи, настоящий JOIN, откат pipeline, откат изменения права при сбое аудита, отзыв прав, отдельность меню от данных и видимость сканирования из другого процесса.
