# Подсистема миграций Auto Admin

## 1. Назначение и концепция

Подсистема миграций Auto Admin предназначена для автоматического и безопасного развёртывания системных таблиц панели управления (`Auto_Admin__*`) в существующей базе данных пользователя (MySQL 8.x).

### Ключевые архитектурные принципы:
1. **Неприкосновенность данных пользователя:** Миграции создают и модифицируют **исключительно** служебные таблицы с префиксом `Auto_Admin__`. Таблицы и данные пользовательского приложения никогда не затрагиваются мигратором.
2. **Пошаговое выполнение (Step-by-Step Execution):** Миграции могут выполняться по одной с фиксацией прогресса на клиенте (UI Wizard), что обеспечивает прозрачность и интерактивность процесса установки.
3. **Одна операция на файл:** `multipleStatements` отключён. Каждый SQL-файл содержит ровно один statement, чтобы результат выполнения был однозначным.
4. **Безопасная остановка:** Состояния `running` и `failed` блокируют обычный runner. Автоматический повтор запрещён, поскольку MySQL DDL может сохраниться даже при последующей ошибке процесса.
5. **Распределённые блокировки (Distributed Locking):** Защита от одновременного запуска миграций несколькими процессами/контейнерами через именованные блокировки MySQL (`GET_LOCK`).

## 2. Структура файлов подсистемы

```text
server/src/migrations/
├── config.ts                        # Константы (имя таблицы истории, имя лока)
├── migration.catalog.ts             # Общий загрузчик каталога из переданной директории
├── migration.errors.ts              # Доменные классы ошибок миграций
├── migration.plan.ts                # Построение плана и валидация порядка/целостности
├── migration.runner.ts              # Оркестрация проверки и выполнения одной миграции
├── migration.recovery.ts            # Контролируемое восстановление
├── migration.types.ts               # Общие типы
├── contracts/                       # Контракт провайдера и репозитория
├── runtime/                         # Выбор активного провайдера
└── providers/mysql/
    ├── mysql-migration.provider.ts  # MySQL-каталог, блокировка и проверка схемы
    ├── migration.repository.ts      # История миграций и аудит восстановления
    ├── migration.verification.ts    # Проверка фактической схемы
    └── sql/                         # 0001–0017: только MySQL SQL
```

## 3. Таблица истории миграций

Вся история выполнения хранится в служебной таблице `Auto_Admin__migration_history`:

```sql
CREATE TABLE IF NOT EXISTS `Auto_Admin__migration_history` (
    version VARCHAR(32) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    file_name VARCHAR(255) UNIQUE NOT NULL,
    checksum CHAR(64) NOT NULL,
    status ENUM('running', 'applied', 'failed') NOT NULL,
    started_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    finished_at DATETIME(3) NULL,
    execution_ms BIGINT UNSIGNED NULL,
    error_message TEXT NULL,
    attempt_count INT UNSIGNED NOT NULL DEFAULT 1,
    app_version VARCHAR(64) NULL,
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### Описание полей:
* `version`: Номер версии (4 цифры, например `0001`). Первичный ключ.
* `name`: Человекочитаемое название миграции.
* `file_name`: Полное имя SQL-файла.
* `checksum`: Контрольная сумма SHA-256 от нормализованного текста SQL.
* `status`: Текущий статус (`running`, `applied`, `failed`).
* `started_at` / `finished_at`: Временные метки начала и завершения с миллисекундной точностью.
* `execution_ms`: Время выполнения скрипта в миллисекундах.
* `error_message`: Текст ошибки MySQL в случае сбоя (до 4000 символов).
* `attempt_count`: Счётчик попыток, зарезервированный для будущего явного recovery-процесса. Обычный runner существующую запись не перезаписывает.
* `app_version`: Версия приложения Auto Admin на момент применения; может быть `NULL`, пока источник версии приложения не подключён.

## 4. Описание компонентов

### 4.1. Каталог миграций (`migration.catalog.ts`)
* Сканирует директорию, переданную провайдером. Сейчас MySQL-провайдер использует `providers/mysql/sql/`.
* Проверяет формат имен файлов по регулярному выражению: `/^(\d{4})__([a-zA-Z0-9_]+)\.sql$/`.
* Проверяет отсутствие дубликатов версий и имен.
* Сортирует файлы по возрастанию версии.
* **Нормализация строк:** Заменяет все Windows-переводы строк `\r\n` на Linux `\n` и обрезает краевые пробелы (`.trim()`).
* Вычисляет детерминированный SHA-256 хеш от нормализованной строки в кодировке UTF-8.

### 4.2. Управление блокировками (`providers/mysql/mysql-migration.provider.ts`)
* Использует функцию MySQL `GET_LOCK('auto-admin:migrations', timeoutSeconds)`.
* При `timeout = 0` попытка взятия лока неблокирующая: если лок занят другим процессом, немедленно выбрасывается `MigrationLockUnavailableError`.
* Снятие лока (`RELEASE_LOCK`) выполняется в блоке `finally`. Если результат не подтверждён или запрос завершился ошибкой, соединение удаляется из пула и ошибка передаётся вызывающему коду.
* При завершении сессии MySQL автоматически освобождает её именованные блокировки.

### 4.3. Соединение мигратора
* Используется одно соединение из активного провайдера БД на всю операцию: захват блокировки, проверка плана, выполнение SQL и обновление истории.
* Обычный путь возвращает соединение в пул. При неподтверждённом освобождении блокировки соединение уничтожается.
* `multipleStatements` не включён: один файл миграции обязан содержать один SQL statement.

### 4.4. Построение плана (`migration.plan.ts`)
Сверяет локальный каталог файлов с историей в базе данных:
1. Для каждой записи строго сверяет позицию, версию, имя, имя файла и SHA-256 checksum.
2. Неизвестная, переименованная или изменённая миграция считается нарушением целостности истории.
3. Все записи истории обязаны иметь статус `applied`.
4. При статусе `running` или `failed` выбрасывается `MigrationRecoveryRequiredError`; последующие миграции не выполняются.
5. Pending-список начинается только после полностью проверенного applied-префикса истории.

### 4.5. Раннер (`migration.runner.ts`)
Управляет исполнением одной миграции (`applyNextMigration(expectedVersion)`):
1. Получает соединение от активного провайдера БД.
2. Захватывает блокировку `GET_LOCK`.
3. Загружает текущий план и проверяет, что `expectedVersion === plan.next.version`.
4. Создаёт новую запись истории со статусом `running`. Существующая версия не перезаписывается и приводит к ошибке уникального ключа.
5. Замеряет время и выполняет SQL-скрипт без обычного таймаута коротких запросов.
6. При успехе: обновляет статус на `applied`, фиксирует `finished_at` и `execution_ms`.
7. При ошибке: обновляет статус на `failed`, записывает `error_message` и пробрасывает исходную ошибку.
8. В блоке `finally` освобождает lock; провайдер затем возвращает безопасное соединение в пул.

### 4.6. Почему DDL не оборачивается в транзакцию

MySQL выполняет неявный `COMMIT` для многих DDL-команд, включая `CREATE TABLE` и `ALTER TABLE`. Поэтому транзакция не может гарантировать совместный откат изменения схемы и записи истории.

Для обнаружения неопределённого состояния runner сначала записывает `running`, а затем выполняет SQL. Если процесс завершился между выполнением DDL и записью `applied`, история останется в `running`, и дальнейшее автоматическое выполнение будет остановлено.

## 5. Правила написания новых SQL-миграций

1. **Именование файлов:**
   Формат: `XXXX__Auto_Admin__<feature_name>.sql`, где `XXXX` — четырехзначный порядковый номер с ведущими нулями (например, `0008__Auto_Admin__permissions.sql`).
2. **Один statement:**
   В файле должна находиться ровно одна SQL-операция. Несколько связанных изменений разбиваются на последовательные версии.
3. **Идемпотентность там, где она не скрывает ошибку:**
   * Для первичного создания служебной таблицы допустим `CREATE TABLE IF NOT EXISTS`.
   * Seeds должны явно определять поведение при конфликте (`ON DUPLICATE KEY UPDATE` или `INSERT IGNORE`).
   * Идемпотентность не является разрешением на автоматический retry и не заменяет проверку фактической схемы.
4. **Изоляция префикса:**
   Все системные объекты обязаны иметь префикс `Auto_Admin__`. Создание таблиц без этого префикса категорически запрещено.

## 6. Состояния ошибки и recovery

### `failed`

SQL-запрос вернул ошибку, после чего runner сохранил её в `error_message`. Обычный запуск не повторяет такую миграцию.

### `running`

Процесс мог аварийно завершиться до фиксации результата. DDL при этом мог как примениться, так и не примениться, поэтому автоматический повтор особенно опасен.

### Правила восстановления

Recovery является отдельной контролируемой операцией. Перед её выполнением необходимо:

1. сверить запись истории с неизменённым файлом и checksum;
2. проверить фактическое состояние схемы;
3. явно выбрать действие: подтвердить уже применённую миграцию либо разрешить контролируемую повторную попытку;
4. сохранить аудиторскую информацию о решении и новой попытке.

Редактирование checksum существующей записи и безусловный upsert статуса запрещены.

## 7. Сборка и деплой (Production Build)

Компилятор TypeScript (`tsc`) компилирует только `.ts` файлы и игнорирует `.sql` файлы.

Для доставки SQL-файлов в продакшн в `server/package.json` настроен скрипт сборки:

```json
"scripts": {
  "build": "node -e \"require('fs').rmSync('dist', { recursive: true, force: true })\" && tsc && node -e \"require('fs').cpSync('src/migrations/providers/mysql/sql', 'dist/migrations/providers/mysql/sql', { recursive: true })\""
}
```

При выполнении `npm run build` MySQL-миграции копируются в `dist/migrations/providers/mysql/sql/`. Провайдер ищет каталог относительно своего скомпилированного файла, поэтому одинаково работает из `src` и `dist`. При добавлении другой СУБД её собственную папку SQL также необходимо включить в сборку. Перенос файлов без изменения их содержимого не меняет checksum уже применённых миграций.
