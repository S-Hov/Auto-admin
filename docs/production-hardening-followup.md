# Повторный аудит production hardening

Дата проверки: 24 августа 2026 года  
Проверенный commit: `c84e639`  
Основание: `docs/production-hardening-plan.md`

Этот документ содержит только оставшиеся задачи после выполнения первоначального плана. Старый план сохраняется как описание целевой модели и причин принятых решений.

## Что уже сделано хорошо

- Весь `/api/install` защищён единым middleware с setup token.
- Setup token сравнивается по SHA-256 через `timingSafeEqual`, а отсутствующий и неверный токен получают одинаковый `401`.
- Bootstrap endpoint остался публичным.
- Для подключения к БД добавлены Zod-валидация, `connectTimeout`, уникальный временный файл, права `0600` и атомарный `rename`.
- Регистрация первого администратора защищена setup token, статусом установки и повторной проверкой внутри транзакции.
- Минимальная длина пароля администратора увеличена до 12 символов.
- Миграции проверяются по порядку, имени файла, имени миграции и checksum.
- Применение миграции выполняется под MySQL advisory lock; клиент не может выбрать произвольную следующую версию.
- `running` и `failed` не запускаются повторно автоматически.
- Login теперь резервирует попытку в MySQL до bcrypt. Это существенно закрывает старую гонку, при которой параллельные запросы сначала читали одинаковый старый счётчик.
- Добавлены централизованная проверка env, production CORS-конфигурация и graceful shutdown.
- Контейнеры запускаются не от root, а `node_modules` вынесены в named volumes.
- Сервер проходит TypeScript-проверку.
- `npm audit --omit=dev` для клиента и сервера: 0 известных уязвимостей.
- Реальные `.env` и setup token не отслеживаются Git.

## Этап 1. Вернуть проект в собираемое и запускаемое состояние

Это нужно сделать до дальнейшего hardening: сейчас свежая версия проекта не имеет воспроизводимого рабочего запуска.

### 1.1. Исправить ошибку TypeScript клиента

Файл: `client/src/features/install-database/ui/InstallDatabaseForm.tsx`.

Сейчас выполняется `delete data.install_token`, хотя `install_token` — обязательное поле типа. Из-за этого клиент не компилируется с `TS2790`.

Нужно:

1. Не изменять объект формы.
2. Деструктурировать его на `install_token` и остальные реквизиты подключения.
3. Создать отдельный тип тела API подключения, в котором setup token отсутствует.
4. Изменить `checkTheConnection`, чтобы она принимала именно этот API-тип, а не полный тип формы.

Критерий:

```bash
npx tsc -b --noEmit
```

завершается без ошибок в `client`.

### 1.2. Синхронизировать API-порт клиента и Docker

Файлы:

- `client/src/shared/api/apiClient.ts`;
- `docker-compose.yml`;
- при необходимости клиентский `.env.example`.

Клиент по умолчанию обращается к порту `8880`, а Docker публикует сервер на `5180`. Без отдельно заданного `VITE_API_URL` браузер обращается не туда.

Нужно выбрать один контракт:

- либо передавать клиенту `VITE_API_URL=http://localhost:5180`;
- либо использовать reverse proxy и относительный `/api`;
- либо согласовать опубликованный порт compose с текущим fallback.

Для production предпочтителен same-origin reverse proxy и относительный `/api`: это упрощает CORS и secure cookies.

Критерий: чистый `docker compose up --build` позволяет клиенту получить `/api/bootstrap/status` без ручного редактирования исходников.

### 1.3. Сделать fresh-clone запуск воспроизводимым

Сейчас сервер требует `Auto_Admin__INSTALL_TOKEN`, но `docker-compose.yml` его не передаёт, а `server/.env.example` нельзя безопасно копировать как готовый env:

- `Auto_Admin__NODE_ENV=development | production | test` не является допустимым значением;
- `Auto_Admin__INSTALL_TOKEN=(openssl rand -hex 32)` является буквальной строкой, а не выполнением команды;
- у DB-переменных отсутствует синтаксис `KEY=value`;
- нет примера CORS-переменной.

Нужно:

1. Превратить `.env.example` в синтаксически валидный шаблон с комментариями.
2. Описать отдельной командой генерацию токена.
3. Передавать токен контейнеру через compose environment/env file, не записывая настоящий секрет в Git.
4. Добавить короткую инструкцию первого запуска.

Критерий: новый разработчик клонирует проект, создаёт env по инструкции и запускает его без поиска скрытых настроек.

## Этап 2. Завершить migration recovery и устранить тупиковые состояния

### 2.1. Добавить recovery stage на клиент

Сервер уже возвращает `migration_recovery_required`, но его нет в:

- `client/src/shared/api/bootstrap/bootstrap.types.ts`;
- `client/src/app/routing/guards/AppGate.tsx`.

Нужно добавить тип и отдельное безопасное состояние интерфейса. До реализации recovery API экран должен хотя бы:

- заблокировать обычный install/auth flow;
- сообщить, что требуется восстановление миграции;
- предложить повторную диагностику;
- не показывать SQL, checksum, путь файла или полный текст SQL-ошибки.

### 2.2. Вернуть корректный API-конфликт для завершённых миграций

Файл: `server/src/shared/middleware/requirePendingMigrations.ts`.

Сейчас завершённые миграции превращаются в обычный `Error`, поэтому глобальный handler отвечает `500`. Это не системная авария, а ожидаемый конфликт состояния.

Нужно вернуть `409` через общий `conflict(...)` со стабильным кодом, например `INSTALL.MIGRATIONS_ALREADY_COMPLETED`.

### 2.3. Устранить окно между последней миграцией и installation status

Последняя миграция помечается `applied` внутри migration runner, а `Auto_Admin__installation.status = migrated` записывается позже, через pool и уже вне migration lock. Если второй шаг упадёт, получится состояние:

- план миграций завершён;
- installation status всё ещё `new`;
- bootstrap возвращает `system_error`;
- повторный `apply-next` заблокирован middleware.

Нужно спроектировать идемпотентное завершение установки. При полностью применённом плане сервер должен уметь безопасно довести installation status до `migrated`, не повторяя SQL-миграцию. Эта операция должна быть сериализована с migration runner и покрыта тестом сбоя между двумя записями.

### 2.4. Реализовать настоящий recovery API

Сейчас добавлен только bootstrap stage. Остальная часть этапа 5 старого документа не реализована.

Recovery API должен:

- требовать setup/recovery token;
- работать под migration lock;
- заново читать каталог и history после получения lock;
- принимать version и checksum как optimistic precondition;
- поддерживать только явные решения `retry` и `mark-applied`;
- не перезаписывать сведения о предыдущей попытке;
- записывать отдельное recovery event/attempt;
- проверять схему перед `mark-applied`.

До появления этих гарантий автоматический retry добавлять нельзя.

## Этап 3. Закрыть оставшиеся риски установки

### 3.1. Запретить обычную замену БД при `database_unavailable`

`canConfigureDatabase` всё ещё разрешает обычный `/check-connection` и при `database_required`, и при `database_unavailable`.

Setup token защищает endpoint от постороннего человека, но не защищает владельца от случайной замены конфигурации временно недоступной production-БД.

Нужно:

- обычный endpoint разрешать только при `database_required`;
- для `database_unavailable` сделать отдельный recovery endpoint;
- потребовать явное подтверждение замены конфигурации.

### 3.2. Сериализовать сохранение DB-конфигурации

Уникальный временный файл защищает от повреждения одного temp-файла, но два параллельных валидных запроса всё ещё могут пройти старую bootstrap-проверку и последовательно перезаписать `.env`; победит последний.

Нужно:

- добавить server-side mutex на операцию проверки и сохранения;
- после получения mutex повторно прочитать bootstrap state;
- удалить временный файл в `finally`, если запись или rename не завершились;
- только после успешного rename обновлять `process.env` и сбрасывать pool.

### 3.3. Довести runtime-валидацию

В `checkConnectionSchema`:

- port должен быть целым числом;
- database, user и password должны иметь максимальную длину;
- должна быть выбрана явная политика неизвестных полей.

В `checkConnection()` убрать `any` для результата `SELECT VERSION()` и описать тип строки mysql2.

### 3.4. Ограничить abuse установочных маршрутов

Нужно добавить:

- разумный лимит `express.json`, например 32–64 KiB;
- rate limit на `/check-connection`;
- небольшой rate limit на создание администратора;
- при необходимости allowlist/CIDR-политику MySQL host для строгих deployments.

Setup token — обязательный первый барьер, но украденный токен не должен давать неограниченный SSRF/connect или bcrypt abuse.

### 3.5. Определить жизненный цикл setup token

Текущая env-схема требует token при каждом запуске. Поэтому рекомендация «удалить token после установки» сейчас остановит сервер.

Нужно явно выбрать и задокументировать одну модель:

- token остаётся как recovery secret, регулярно ротируется и хранится во внешнем secret store;
- либо после `ready` server может стартовать без install token, но recovery требует отдельно включить новый token.

Пока обычный endpoint разрешён при `database_unavailable`, оставлять постоянный token особенно рискованно.

### 3.6. Не хранить setup token в Web Storage

Первоначальный план требовал хранение только в React memory. Сейчас используется `sessionStorage`, который доступен любому JavaScript в origin при XSS. Кроме того, поле token отображается как обычный `text`.

Нужно:

- хранить token в отдельном install context в памяти;
- после перезагрузки запрашивать его повторно;
- очищать при `ready` централизованно, а не только в success callback формы;
- отображать поле как `password` с осознанной кнопкой показа при необходимости.

## Этап 4. Завершить защиту login

Текущий порядок `INSERT attempt -> SELECT counters -> bcrypt` является заметным улучшением и не повторяет прежнюю очевидную гонку. Переписывать его только ради другой архитектуры не нужно до появления теста, который доказывает проблему.

Оставшиеся задачи:

1. Написать интеграционный тест на 20 параллельных запросов и зафиксировать точную семантику порога: сейчас пятый запрос пары user+IP уже блокируется, то есть проверку пароля проходят максимум четыре.
2. Явно преобразовывать результаты `SUM()` mysql2 в проверенные числа.
3. Добавить индекс `(username, created_at)`.
4. Добавить периодическую retention-очистку старых `login_attempts`; сейчас таблица растёт бесконечно.
5. Добавить быстрый route-level burst limiter до MySQL и bcrypt.
6. Возвращать `Retry-After` вместе с `429`.
7. Вынести лимиты и окна времени в типизированную конфигурацию.
8. Настроить точный `trust proxy` для конкретной production-схемы. Не использовать безусловный `true`.
9. Измерить bcrypt cost на целевом сервере и проверить, что параллельные login/register не блокируют event loop недопустимо долго.

## Этап 5. Production infrastructure и наблюдаемость

### 5.1. Исправить env-контракт

- Переименовать `Auto_admin__CORS_ALLOWED_ORIGINS` в `Auto_Admin__CORS_ALLOWED_ORIGINS` во всех местах.
- Валидировать PORT как целое число `1..65535`.
- Не допускать пустой HOST.
- Использовать `envConfig` для системных переменных последовательно, не смешивая его с прямым `process.env` без причины.
- DB-переменные оставить динамическими: они законно появляются после первого запуска, поэтому их нельзя навсегда «заморозить» в объекте, созданном до установки.

### 5.2. Укрепить graceful shutdown

Добавить флаг начала shutdown, чтобы повторные SIGINT/SIGTERM не запускали cleanup и аварийные таймеры несколько раз. Затем проверить завершение активной миграции и обычного DB-запроса в интеграционном тесте.

### 5.3. Добавить production logging

Текущий logger всё ещё использует `console.log`.

Нужно:

- структурированный JSON logger;
- request ID в запросе, ответе и error log;
- уровни логов;
- redaction для cookie, authorization, setup-token, password и DB password;
- stack неизвестной ошибки только в серверном логе;
- логирование неожиданных bootstrap-ошибок перед возвратом `system_error` — сейчас bootstrap их полностью проглатывает.

### 5.4. Добавить таймауты по уровням

Нужны отдельные политики для:

- MySQL connect;
- пользовательского query execution;
- HTTP request/headers;
- graceful shutdown.

`connectTimeout` не ограничивает уже запущенный тяжёлый SQL.

### 5.5. Завершить общую инфраструктуру API

- единый каталог error codes через `as const`;
- общий helper опций auth cookie для set/clear;
- request body type не должен содержать `any` без необходимости;
- фасады `auth.queries.ts` и `bootstrap.queries.ts` переименовать в `*.facade.ts` либо заменить публичными `index.ts`-функциями.

### 5.6. Отделить dev Docker от production image

Текущие Dockerfile запускают dev/watch server, выполняют `npm install` и bind-mount исходников. Это нормальная локальная конфигурация, но не production image.

Нужно создать отдельный production target/compose:

- `npm ci` по lock-файлу;
- multi-stage build;
- запуск server из `dist`;
- гарантированное копирование SQL-файлов миграций;
- статическая сборка клиента за reverse proxy;
- MySQL/Adminer не публикуются наружу без явной необходимости;
- реальные пароли MySQL не захардкожены.

## Этап 6. Автоматические тесты — обязательный критерий завершения

Сейчас в package scripts нет test runner, поэтому конкурентные и recovery-гарантии подтверждены только чтением кода и ручным прогоном.

Минимальный набор перед публичным релизом:

1. Unit: `buildMigrationPlan`, каталог файлов, checksum, query compiler.
2. Integration с настоящим MySQL: пустая база, все миграции, stale expectedVersion, два параллельных apply-next.
3. Migration failure: `running`, `failed`, изменённый checksum, сбой после последней миграции до обновления installation status.
4. Install auth: отсутствующий, неверный и правильный token на каждом install endpoint.
5. Параллельное создание администратора: создаётся ровно один.
6. Auth: login/logout/getMe, inactive/revoked/expired session, последовательный и параллельный brute force, retention.
7. Proxy: IP корректно определяется только при ожидаемом числе trusted hops.
8. Production build: SQL-файлы находятся в `dist`, server/client собираются из чистого checkout.

## Отдельно: новый query engine пока нельзя подключать к API

`server/src/core/query-engine/compiler/mysql.compiler.ts` сейчас является незавершённой заготовкой:

- `compileRead` игнорирует `where`, joins, sort, limit и offset;
- неизвестный comparison operator превращается в некорректный SQL;
- `_null`/`_not_null` игнорируют переданное boolean-значение;
- пустой `_not` создаёт `NOT ()`;
- нет runtime Zod-валидации глубины, количества условий и размера `_in`;
- identifier escaping не заменяет allowlist таблиц/колонок и проверку прав пользователя;
- `table.*` экранируется некорректно как обычное имя `*`.

Пока compiler нигде не вызывается, это не эксплуатируемая уязвимость. Подключать его к route можно только после runtime-валидации, schema allowlist, permission layer, query limits и unit-тестов на SQL/params.
