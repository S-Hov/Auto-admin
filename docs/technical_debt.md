# Реестр технического долга и задач по повышению надежности (Production Readiness)

В этом документе зафиксированы выявленные архитектурные зоны роста, потенциальные риски и задачи по доведению бэкенда до стандартов отказоустойчивого энтерпрайз-продакшна.

---

## 1. Высокий приоритет (Production Hardening & Reliability)

### 1.1. Отсутствие Graceful Shutdown (Корректное завершение процесса)
* **Файлы:** [`server/src/app.ts`](file:///home/hov/Projects/auto-admin/server/src/app.ts), [`server/src/db/index.ts`](file:///home/hov/Projects/auto-admin/server/src/db/index.ts)
* **В чём риск:** 
  При перезапуске контейнера (в Docker / Kubernetes / systemd) процессу отправляется сигнал `SIGTERM`. Сейчас сервер обрывает процесс мгновенно. Если в этот момент выполнялся HTTP-запрос или транзакция в базу, транзакция оборвётся, сокеты зависнут, а клиент получит сетевую ошибку 502/Drop.
* **Решение:**
  1. Добавить перехват сигналов `SIGTERM` и `SIGINT`.
  2. Остановить приём новых входящих HTTP-соединений через `server.close()`.
  3. Дождаться завершения текущих активных запросов (с таймаутом, например 10 секунд).
  4. Закрыть пул соединений с базой данных `await pool.end()`.
  5. Завершить процесс `process.exit(0)`.

### 1.2. Прямой и невалидированный доступ к `process.env`
* **Файлы:** [`server/src/app.ts`](file:///home/hov/Projects/auto-admin/server/src/app.ts), [`server/src/db/index.ts`](file:///home/hov/Projects/auto-admin/server/src/db/index.ts), [`server/src/modules/bootstrap/bootstrap.service.ts`](file:///home/hov/Projects/auto-admin/server/src/modules/bootstrap/bootstrap.service.ts)
* **В чём риск:**
  Переменные окружения читаются напрямую по всему коду (`process.env.Auto_Admin__PORT`, `process.env.Auto_Admin__DB_HOST!`). Если обязательная переменная не задана или содержит мусор (например, строку вместо числа в порте), ошибка выстрелит в рантайме в самый неожиданный момент во время пользовательского запроса.
* **Решение:**
  Создать централизованный модуль конфигурации `server/src/config/env.ts`:
  * Валидировать все системные переменные на старте через Zod-схему.
  * Экспортировать строго типизированный объект `config`.
  * Если конфигурация некорректна — сервер должен падать с понятным описанием ошибки ещё до запуска HTTP-лиссенера (Fail-fast принцип).

### 1.3. Захардкоженный массив CORS Origins
* **Файлы:** [`server/src/app.ts`](file:///home/hov/Projects/auto-admin/server/src/app.ts#L13-L22)
* **В чём риск:**
  Массив `defaultAllowedOrigins` содержит только `localhost` и `127.0.0.1` на портах `5173..5177`. При развёртывании админки на реальном домене (например, `admin.mycompany.com`) браузер заблокирует все запросы по политике CORS.
* **Решение:**
  * Вынести список разрешённых origins в переменную окружения (например, `Auto_Admin__CORS_ALLOWED_ORIGINS=https://admin.domain.com,http://localhost:5173`).
  * В `app.ts` парсить эту строку и динамически проверять входящий заголовок `Origin`.

## 2. Средний приоритет (Observability & Testing)

### 2.1. Логирование на `console.log` вместо структурированного JSON-логгера
* **Файлы:** [`server/src/shared/middleware/logger.ts`](file:///home/hov/Projects/auto-admin/server/src/shared/middleware/logger.ts), [`server/src/shared/middleware/errorHandler.ts`](file:///home/hov/Projects/auto-admin/server/src/shared/middleware/errorHandler.ts)
* **В чём риск:**
  `console.log` не подходит для продакшна: логи не имеют единого формата, их тяжело парсить в системах сбора логов (Grafana Loki, ELK, Datadog), нет разделения по уровням (`info`, `warn`, `error`), нет сквозного `requestId`, есть риск случайно распечатать чувствительные данные (пароли, хеши, токены).
* **Решение:**
  * Подключить быстрый структурированный JSON-логгер (например, `pino` или `winston`).
  * Генерировать уникальный `requestId` (UUID / nanoid) для каждого входящего HTTP-запроса и пробрасывать его через весь контекст выполнения.
  * Настроить автоматическое маскирование (masking/redacting) полей `password`, `token`, `passwordHash`.

---

### 2.2. Отсутствие автоматизированных интеграционных и Unit-тестов
* **Файлы:** Каталоги `server/src/modules/`, `server/src/migrations/`
* **В чём риск:**
  При добавлении новых фич (например, интроспекции таблиц или динамического построителя запросов) есть риск незаметно сломать миграции, логин или rate-limiting (регрессионные ошибки).
* **Решение:**
  Настроить тестовый фреймворк (Vitest или Jest + Supertest):
  1. **Интеграционные тесты миграций:** Поднять реальный тестовый MySQL (через Docker/Testcontainers), накатить миграции с 1 по 7, проверить статус и расчет чексумм.
  2. **Тесты установки и авторизации:** Проверить создание первого админа, попытку создать второго (ожидаем 409), проверку rate-limiting (после 5 неверных попыток ожидаем 429).
  3. **Unit-тесты:** Проверка построения плана миграций (`buildMigrationPlan`) и валидации Zod-схем.

---

### 2.3. Отсутствие таймаутов на выполнение запросов к БД
* **Файлы:** [`server/src/db/index.ts`](file:///home/hov/Projects/auto-admin/server/src/db/index.ts)
* **В чём риск:**
  Если к автоадминке подключат тяжелую базу с таблицами на миллионы записей без индексов, «тяжелый» запрос может повесить соединение MySQL на минуты, забив пул соединений и парализовав всю админку.
* **Решение:**
  * Настроить таймаут выполнения запросов на уровне пула `connectTimeout` / `queryTimeout` в драйвере `mysql2` или задавать явный `max_execution_time` для пользовательских запросов.

## 3. Низкий приоритет (Рефакторинг и полировка)

### 3.1. Единый реестр кодов ошибок (Error Catalog)
* **Файлы:** [`server/src/shared/api/errors/`](file:///home/hov/Projects/auto-admin/server/src/shared/api/errors/)
* **В чём риск:**
  Строковые коды ошибок (`'INSTALL.MIGRATIONS_ALREADY_COMPLETED'`, `'AUTH.UNAUTHORIZED'`) сейчас пишутся вручную строками в разных сервисах. Возможны опечатки и рассинхронизация с фронтендом.
* **Решение:**
  Создать единый TypeScript `enum` или `const ErrorCodes = { ... } as const` и использовать его во всех сервисах и контроллерах.

---

### 3.2. Централизация опций сессионных Cookies
* **Файлы:** [`server/src/modules/auth/auth.controller.ts`](file:///home/hov/Projects/auto-admin/server/src/modules/auth/auth.controller.ts)
* **В чём риск:**
  Параметры `httpOnly: true`, `sameSite: 'lax'`, `secure: ...`, `path: '/'` дублируются в `loginController` и `logoutController`. При изменении настроек безопасности можно забыть обновить один из них.
* **Решение:**
  Вынести генерацию параметров cookie в хелпер `getAuthCookieOptions(expiresAt?: Date)`.

| Задача | Область | Критичность | Влияние на продакшн |
| :--- | :--- | :--- | :--- |

| **Централизованный Config (Zod)** | Конфигурация | 🔴 Высокая | Защита от запуска сервера с некорректными/пустыми переменными |

| **Автотесты (Vitest + Supertest)** | Качество | 🟡 Средняя | Защита от регрессий и сломанных миграций |
| **Query Timeouts** | База данных | 🟡 Средняя | Защита пула от зависания на тяжелых запросах |
| **Error Codes Catalog** | API Контракты | 🟢 Низкая | Удобство интеграции с React-клиентом |
| **Cookie Options Helper** | Авторизация | 🟢 Низкая | Исключение дублирования настроек безопасности кук |
