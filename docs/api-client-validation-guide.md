# Валидация ответов API

Каждый endpoint передаёт в `apiClient(path, responseSchema, options)` обязательную Zod-схему **полного ответа**, а не только `data`. Общий `apiResponseSchema(dataSchema)` сохраняет формат `{ success: true, code, data }` и требует `data` для endpoint-ов с полезной нагрузкой.

Схемы находятся рядом с модулями в `*.schema.ts`. Типы ответов в `*.types.ts` выводятся из схем через `z.infer`; типы запросов остаются отдельными. При добавлении endpoint-а нужно сверить обязательность полей с существующим серверным контрактом и добавить проверку корректного и некорректного ответа.

Используем `z.looseObject`, чтобы сохранять дополнительные поля сервера. Числа, boolean, enum и nullable-поля проверяются без coercion, defaults и преобразования значений. Если endpoint возвращает успех без `data`, можно передать `apiSuccessSchema` напрямую.

Корректные ошибки `{ success: false, code, params?, details? }` превращаются в существующий `ApiClientError`, включая ошибки в HTTP 200. Ошибочные HTTP-ответы без корректного error-envelope сохраняют прежний fallback `COMMON.UNKNOWN_ERROR`. Некорректный успешный ответ вызывает `ApiContractError`; `cause` содержит ошибки Zod, а `status` — HTTP-статус. Ошибки сети и отмены запроса сохраняются от `fetch`.

Cookies, заголовки установки, `FormData` и переданный `AbortSignal` сохраняют прежнее поведение. Общего таймаута нет: установка и миграции могут выполняться дольше трёх секунд.

Работа над тестовым меню и его Zod-валидацией находится в отдельной ветке `S-Hov/admin-menu-layouts` и не входит в миграцию API. После объединения веток локальную проверку mock-ответа можно перевести на общий `parseApiResponse`; для подключения сервера — использовать `apiClient('/menu', menuResponseSchema)`.
