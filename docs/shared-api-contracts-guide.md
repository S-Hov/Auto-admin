# Общие API-контракты клиента и сервера

Статус: план внедрения и точка продолжения работы.
Дата: 29 октября 2026 года.

## 1. Зачем мы это делаем

Сейчас клиент и сервер местами отдельно описывают одну и ту же структуру запроса или ответа. Например, формат `PageConfig` нужен серверу для проверки сохранения страницы, а клиенту — для проверки ответа и отображения страницы.

Две вручную поддерживаемые схемы могут разойтись. Поэтому создаём отдельный пакет `@auto-admin/contracts`, из которого обе стороны импортируют одинаковые Zod-схемы и TypeScript-типы.

**Схему пишем один раз. Генерировать клиентскую копию схемы не будем.** Генерация JavaScript и файлов типов при сборке — другое дело: это обычный результат компиляции одного источника.

## 2. Как устроен репозиторий

```text
auto-admin/
  package.json                 ← объявляет npm workspaces
  package-lock.json            ← появится после общей установки зависимостей
  packages/
    contracts/
      package.json
      tsconfig.json
      src/                     ← общие исходники
        common/
        pages/
        menu/                  ← следующие этапы
        auth/                  ← следующие этапы
      dist/                    ← результат сборки, не исходники
  client/
  server/
```

Workspace — отдельный пакет внутри общего репозитория. npm умеет устанавливать его зависимости и связывать его с соседними пакетами без ручного копирования файлов.

Само наличие `workspaces` ещё не создаёт рабочую библиотеку. Нужны исходники, сборка, публичные экспорты и зависимости приложений на этот пакет.

## 3. Что уже сделано

Проверено по файлам на момент создания документа:

- В корневом `package.json` объявлены `client`, `server`, `packages/contracts`.
- Корневой проект помечен `private: true`.
- Создан `packages/contracts/package.json` с именем `@auto-admin/contracts`, версией `0.1.0` и `private: true`.
- Выбран `type: commonjs` для совместимости с текущим сервером.
- Указана зависимость Zod `^4.4.3`.
- Добавлены команды `build` и `dev` для компиляции и watch-режима TypeScript.
- Добавлен TypeScript `^6.0.3` в devDependencies пакета.
- Создан `tsconfig.json`: ES2022, NodeNext, `src` → `dist`, `declaration: true`, `strict: true`.

Есть два отличия от первоначального предложения, оба допустимы:

- `skipLibCheck: false` означает, что TypeScript также проверяет декларации зависимостей. Это не ошибка; если возникнут сторонние проблемы или лишние затраты времени, можно отдельно обсудить `true`.
- TypeScript записан как `^6.0.3`, а предлагалось `~6.0.3`. `^` допускает новые minor-версии в пределах major 6, `~` — только patch-обновления ветки 6.0. Для более узкого диапазона можно выбрать `~`, но для самой архитектуры это не принципиально. Точные установленные версии фиксирует lock-файл.

Завершающие запятые в `tsconfig.json` допустимы: TypeScript поддерживает JSON с комментариями и такими запятыми. В обычном `package.json` они недопустимы.

**Публичные экспорты ещё не настроены. Исходные схемы не перенесены. Клиент и сервер пакет ещё не используют. Общая установка зависимостей и сборка в рамках этой работы не запускались.** В текущем пакете пока нет файлов исходного кода; сборка без них может сообщить, что входные файлы не найдены.

## 4. Что лежит в общем пакете

Разрешено переносить:

- Zod-схемы запросов и ответов API.
- Схему `PageConfig` и её вложенных объектов.
- Типы, выведенные через `z.infer`, `z.input`, `z.output`.
- Общие ограничения, например максимальный размер страницы.
- Структуру успешного ответа, ошибки, параметров перевода и ошибок полей.
- Позже — публичные коды ошибок и успехов, если решим объединить и их.

Не переносим:

- Express-контроллеры, middleware и HTTP Response.
- Репозитории, SQL, подключения, переменные окружения и секреты.
- Проверку существования таблиц и полей по каталогу.
- Проверки прав и бизнес-правила системных операций.
- React-компоненты, хуки, формы и клиентские тексты переводов.
- Внутренние типы строк БД только ради повторного использования типа.

Общий пакет не должен импортировать код из `client` или `server`. Направление зависимостей только такое: приложения зависят от контрактов, а не наоборот.

## 5. Пример использования

Внутри пакета находится схема и выведенный из неё тип:

```ts
export const pageConfigSchema = z.strictObject({
    // Единое описание конфигурации.
});

export type PageConfig = z.infer<typeof pageConfigSchema>;
```

Обе стороны затем импортируют:

```ts
import {
    pageConfigSchema,
    type PageConfig,
} from '@auto-admin/contracts/pages';
```

В результате IDE подсказывает поля, а runtime-валидация проверяет фактически полученный JSON. TypeScript сам по себе не проверяет сетевые данные.

Сервер продолжает проверять контракт входящего запроса, затем права, наличие ресурсов и бизнес-правила. Клиент проверяет контракт ответа. Совместное использование схем не делает клиента доверенным.

## 6. JavaScript и подсказки IDE

Сборка пакета превращает исходники в два вида файлов:

```text
src/pages/index.ts
        ↓ TypeScript
dist/pages/index.js       ← выполняемый код, включая Zod-схемы
dist/pages/index.d.ts     ← объявления типов для IDE и TypeScript
```

`declaration: true` включает создание `.d.ts`. Интерфейсы в этих файлах не нужно писать вручную.

Клиентская сборка должна уметь подключать CommonJS-пакет, а сервер — выполнять его через текущую систему модулей. Совместимость проверяем реальной сборкой и импортом результата, а не только наличием подсказок IDE. При необходимости настроим предсборку зависимости в Vite; не добавляем такую настройку без проверки.

## 7. Публичные экспорты пакета — следующий шаг

Создаём исходные точки входа `src/common/index.ts` и `src/pages/index.ts`. Из них экспортируем только публичные схемы, типы и ограничения соответствующего раздела.

Затем добавляем в `packages/contracts/package.json` явные subpath-экспорты. Пример направления настройки:

```json
{
  "exports": {
    "./common": {
      "types": "./dist/common/index.d.ts",
      "default": "./dist/common/index.js"
    },
    "./pages": {
      "types": "./dist/pages/index.d.ts",
      "default": "./dist/pages/index.js"
    }
  },
  "files": ["dist"]
}
```

Это фрагмент, а не замена существующего манифеста. Пути должны совпадать с реальным результатом сборки.

Не нужно импортировать `@auto-admin/contracts/src/...` или соседний серверный файл по относительному пути. Публичный импорт проходит через `exports`, а приложение получает уже собранную библиотеку.

Первой переносим существующую чистую схему `page-config.schema.ts`. Для сохранения старых импортов на сервере можно временно оставить в прежнем файле переэкспорт из общего пакета. Схема при этом существует только в одном месте.

Далее переносим чистые схемы параметров и описываем ответы страниц. Проверка конфига по каталогу и сборщик запросов остаются в серверном модуле pages.

## 8. HTTP-параметры и обычные объекты

Не смешиваем два представления:

```text
HTTP:      limit="25", offset="0", sortField="total", sortDirection="desc"
Внутри:    limit=25, offset=0, sort={ field: "total", direction: "desc" }
```

Текущая `pageRowsHttpQuerySchema` преобразует строки и передаёт результат через `.pipe(pageRowsQuerySchema)`. Это разделение сохраняем. Клиентский метод принимает удобный объект с числами, проверяет его и собирает URL; сервер проверяет реальный HTTP-ввод.

Если нужны типы до и после преобразования, используем `z.input` и `z.output`: они могут различаться, особенно при `.default()` и `.transform()`.

## 9. Установка зависимостей и lock-файлы

После подготовки исходников и экспортов:

1. Добавляем `@auto-admin/contracts: "0.1.0"` в dependencies клиента и сервера. Версия совпадает с локальным workspace-пакетом. Не рассчитываем на поддержку протокола `workspace:*` в npm.
2. Выполняем установку из корня репозитория. npm связывает локальный пакет и создаёт общий корневой `package-lock.json`.
3. Проверяем установку, сборку и тесты всех пакетов.
4. После успешной миграции удаляем устаревшие lock-файлы клиента и сервера отдельным осознанным изменением. Источником точной установки становится корневой lock-файл.
5. В CI используем `npm ci` из корня.

Не удаляем заранее пользовательские файлы, не пересоздаём БД и не меняем прикладную логику ради установки workspaces. Существующие каталоги `node_modules` могут содержать зависимости старой установки; чистую воспроизводимость нужно проверить отдельно, а не судить о ней по запуску со старым окружением.

## 10. Порядок сборки и локальная разработка

Контракты собираются до приложений. Целевые команды из корня:

```text
npm run build --workspace=@auto-admin/contracts
npm run build --workspace=server
npm run build --workspace=client
```

Они будут доступны после установки workspaces и подготовки исходников. Для удобства позже добавляем корневые команды, которые выполняют этот порядок, а не запускают все сборки параллельно.

В `client` и `server` нужно продумать предварительную сборку контрактов для прямого запуска их команд: разработчик не должен случайно работать со старым `dist` пакета. При этом не создаём цикл между корневыми scripts и scripts приложений.

Для разработки:

1. Один раз собираем контракты.
2. Запускаем `tsc --watch` пакета в отдельном процессе.
3. Запускаем клиент и сервер.
4. Проверяем, что изменение схемы пересобирает пакет и подхватывается приложениями. Автоматический перезапуск сервера при изменении локальной зависимости нужно проверить отдельно; наблюдение за `node_modules` может быть исключено инструментом запуска.

`dist` — генерируемая папка, её добавляем в `.gitignore`. В CI она строится заново. Если нужны файлы, удалённые из исходников, в сборке предусматриваем безопасную очистку только `packages/contracts/dist`, чтобы старые экспорты не оставались в результате.

## 11. Docker

Сейчас контексты сборки в compose — отдельно `./client` и `./server`. Они не видят `packages/contracts`, поэтому после перехода это нужно изменить.

План:

- Использовать корень репозитория как build context.
- Явно указывать `client/Dockerfile` и `server/Dockerfile`.
- Сначала копировать корневой lock-файл и манифесты workspace-пакетов, выполнять установку, затем копировать нужные исходники и собирать контракты.
- Скорректировать рабочие директории, bind mounts и volumes зависимостей: старый mount `./client:/app` или `./server:/app` не должен скрывать установленный общий пакет и корневой workspace-манифест.
- Настроить корневой `.dockerignore`, исключающий `.git`, `node_modules`, сгенерированные `dist`, локальные `.env`, секреты и прочие ненужные файлы.
- `.env` передавать при запуске, не включать в образ.

Docker-развёртывание пока не изменено. Не считать перенос завершённым, пока сборки образов и запуск не проверены либо явно не зафиксировано, что на текущей машине Docker недоступен.

## 12. Разные машины и CI/CD

Общий пакет не связывает работающие приложения по сети. На каждой машине находится собственный установленный или собранный экземпляр нужного кода.

Вариант A: CI получает весь репозиторий, устанавливает зависимости и собирает контракты, затем клиент и/или сервер.

- На веб-сервер фронтенда доставляется `client/dist`. Нужные Zod-схемы уже входят в JavaScript-бандл.
- На сервер API доставляются серверный `dist`, runtime-зависимости и собранный пакет контрактов.
- При использовании workspace-симлинков нельзя просто скопировать `server/node_modules`: зависимости могут находиться в корне, а ссылка на пакет — вести в `packages/contracts`. Deployment-артефакт обязан сохранять нужную структуру либо устанавливать упакованный пакет как обычную зависимость.

Вариант B: сборка выполняется на целевой машине из полного репозитория. Это тоже допустимо, хотя сборка в CI обычно удобнее для воспроизводимости.

Вариант C на будущее: пакет публикуется с версиями в публичном или приватном npm-реестре. Тогда отдельно лежащие клиент и сервер устанавливают его как обычную зависимость, без исходников соседнего приложения. Перед публикацией пересматриваем `private`, лицензию, содержимое пакета и сборочный процесс; прямо сейчас публикация не нужна.

Docker и CI/CD не взаимоисключающие варианты: CI может собирать и доставлять образы.

## 13. Версии и совместимость

Общая схема предотвращает расхождения в исходниках, но не гарантирует одновременное обновление развёрнутых приложений.

Старый клиент может работать с новым сервером, если изменения совместимы. Добавление обязательного поля, удаление свойства или изменение его смысла может потребовать согласованного обновления или новой версии контракта. Строгие Zod-объекты отклоняют неизвестные поля: это нужно учитывать при развитии API, а не автоматически считать любое добавление совместимым.

Версия npm-пакета, `PageConfig.schemaVersion` и `revision` страницы решают разные задачи:

- версия пакета — версия библиотеки контрактов;
- `schemaVersion` — формат сохранённого конфига;
- `revision` — версия конкретной записи страницы.

## 14. Проверки завершения переноса

- Контракты собираются из исходников в JS и `.d.ts`.
- Клиент и сервер импортируют публичные экспорты пакета, а не внутренние файлы друг друга.
- В клиентский бандл не попадают Express, драйвер БД, секреты или серверные сервисы.
- Схема `PageConfig` больше не поддерживается в двух исходных копиях.
- Прежние тесты схем и модулей pages проходят, TypeScript обеих сторон не выдаёт ошибок.
- Сборка клиента принимает CommonJS-пакет; собранный сервер импортирует его без запуска TypeScript напрямую.
- Общая установка воспроизводится из корневого lock-файла.
- Сборка копирует SQL-каталог миграций как раньше; `server/dist/app.js` остаётся корректной точкой старта.
- Docker видит общий пакет, корректно работает с volumes и не включает `.env` в образ.
- Watch-режим подхватывает изменения схем, а не оставляет устаревший код незаметно.

## 15. С чего продолжить

**Текущая точка остановки: манифесты и tsconfig подготовлены; следующий шаг — исходники и публичные экспорты пакета.**

Порядок дальнейшей работы:

1. Подготовить `src/common` и `src/pages`, перенести чистые контракты и настроить `exports`.
2. Добавить зависимости приложений и выполнить общую установку.
3. Подключить контракты сначала к pages и общему формату API, сохранив при необходимости временные переэкспорты.
4. Настроить сборку, watch, lock-файлы, Docker и проверки.
5. Вернуться к незавершённой задаче: `client/src/shared/api/pages/` со схемами ответов и методами `getPage(pageId)` и `getRows(pageId, params)` на существующем `apiClient`, включая отмену запросов.
6. React-экран, загрузку и отрисовку таблицы пользователь хочет реализовывать сам.

Меню, авторизацию, установку и остальные API переносим позднее по одному модулю. В рамках первого шага не переписываем весь сервер и клиент.
