# Общие API-контракты клиента и сервера

Статус: перенос реализован. Обновлено 3 ноября 2026 года.

## 1. Как это работает

Единый источник транспортных схем — `packages/contracts/src`. Пакет называется `@auto-admin/contracts` и связан с клиентом и сервером через корневые npm workspaces.

Пишем одну Zod-схему, выводим тип через `z.infer`, обе стороны используют её через публичный импорт. Сборка создаёт CommonJS JavaScript и декларации `.d.ts` в `packages/contracts/dist`. Исходники другого приложения импортировать не нужно.

```ts
import { pageConfigSchema, type PageConfig } from '@auto-admin/contracts/pages';
import { loginSchema } from '@auto-admin/contracts/auth';
import { ERROR_CODES } from '@auto-admin/contracts/common';
```

## 2. Что перенесено

| Экспорт | Содержание |
| --- | --- |
| `/common` | Общий API envelope, ошибки полей, параметры переводов, ID, публичные коды ошибок и успехов, типы ответов |
| `/auth` | Запрос входа, ответы входа/выхода и текущего пользователя |
| `/install` | Регистрация администратора, подключение к БД, выбор СУБД, миграции и восстановление, ответы установки |
| `/bootstrap` | Все серверные стадии bootstrap и ответ состояния, включая system_configuration_required |
| `/database` | Публичные идентификаторы СУБД и их описания; без драйверов и подключений |
| `/menu` | Создание/изменение, параметры удаления, права меню и схемы ответов |
| `/pages` | PageConfig, CRUD страниц, список страниц, параметры строк и ответы с пагинацией |
| `/access-control` | Формат правил и субъектов, доступный пользователю каталог и результат сканирования |
| `/query` | JSON-запросы движка, ограничения сложности, HTTP-envelope, описание pipeline и ответы |

Чистые файлы-мосты удалены. Клиент, сервер и тесты импортируют контракты напрямую из `@auto-admin/contracts/...`. На сервере сохранены файлы с реальной логикой: разбором ошибок, внутренними типами аудита, контекстом исполнения и проверками каталога. Публичные `index.ts` серверных подсистем остаются входными точками самих подсистем, а не заменой пакета контрактов.

Типы Zod-схем выводятся из схем. Чистые публичные типы AST и generic-ответов движка также находятся в пакете. Типы подключения, строки SQL-репозиториев, состояние исполнителя и бизнес-объекты остаются на сервере.

## 3. Важные различия имён

- `pageListSchema` — описание списка внутри PageConfig.
- `pageListQuerySchema` — HTTP-параметры поиска самих конфигураций страниц.
- `pageRowsQuerySchema` — обычный объект с числовыми limit/offset и sort.
- `pageRowsHttpQuerySchema` — преобразование строковых HTTP-параметров в этот объект.
- `applyNextMigrationRequestSchema` — запрос выполнения миграции.
- `applyNextMigrationSchema` — данные ответа выполнения миграции, прежнее клиентское имя.

Если прикладной код использует прежнее локальное имя, оно сохраняется через `as` непосредственно в импорте. Отдельного файла ради такого алиаса больше нет.

## 4. Что остаётся вне пакета

Общий пакет не зависит от Express, React, драйверов БД, переменных окружения или приложений.

На сервере остаются:

- проверка таблиц и полей по schema-catalog;
- access-control, правила изменения прав и проверка активного администратора;
- разрешение ссылок и авторизация Query Engine;
- серверные parse-функции, превращающие ошибки Zod в ApiError;
- сервисы, транзакции, аудит, репозитории, SQL и миграции.

На клиенте остаются API-вызовы, переводы, React-компоненты и UI-правила форм. Форма может иметь собственные UI-настройки; транспортный контракт не нужно заново описывать ради формы. Совпадавшая схема регистрации администратора теперь переэкспортирует общий контракт.

Сервер не начинает доверять клиенту: runtime-валидация и проверка прав обязательны на каждом входе.

## 5. Установка и команды

Все зависимости устанавливаются **из корня**:

```sh
npm ci
npm run build:contracts
npm run typecheck
npm test
npm run build
```

Единый lock-файл — корневой `package-lock.json`. Старые lock-файлы клиента и сервера удалены после проверки workspaces. Не запускайте независимую установку с отдельными lock-файлами в приложениях.

`npm run build` собирает сервер и клиент. У приложений есть prebuild, pretest и predev, которые сначала собирают контракты. Сервер продолжает копировать SQL-каталог миграций в `dist/migrations/providers/mysql/sql`.

`dist` контрактов не коммитится: это генерируемый результат. Изменение схем требует пересборки.

## 6. Разработка

В отдельных терминалах из корня:

```sh
npm run dev:contracts
npm run dev --workspace=server
npm run dev --workspace=client
```

Predev выполняет первоначальную сборку, а `dev:contracts` следит за последующими изменениями пакета. Не следует рассчитывать, что один predev автоматически включает наблюдение за контрактами.

В `client/vite.config.ts` публичные entry points контрактов перечислены в `optimizeDeps.include`: пакет собирается в CommonJS, а браузер в dev-режиме загружает ESM. Связанные workspace-пакеты Vite по умолчанию считает исходниками, поэтому им нужна явная предсборка. При добавлении нового entry point обновите этот список. После изменения контрактов для сброса кеша предсборки перезапустите клиент через `npm run dev --workspace=client -- --force`.

Если изменения CommonJS-зависимости не подхватились инструментом запуска, перезапустите соответствующее приложение. Автоматический перезапуск при изменении workspace-зависимости зависит от watcher; в этой работе не заявлено, что весь HMR-сценарий проверен в браузере.

## 7. Docker

Контексты сборки обоих приложений теперь указывают на корень, Dockerfile выбирается явно. Используется Node 22. Сначала копируются манифесты и корневой lock-файл, затем выполняется `npm ci`, копируются исходники и собираются контракты.

Корневой `.dockerignore` исключает `node_modules`, `dist`, `.git`, локальные конфигурации и `.env*`. Секреты не включаются в образ. Compose продолжает передавать окружение серверу при запуске.

В dev-compose корень смонтирован в `/app`, а каталоги зависимостей защищены отдельными named volumes. Для workspace-окружения заданы новые имена volumes: они не используют старые зависимости прежней структуры. Том MySQL и его содержимое не менялись.

После изменения зависимостей Docker-окружение нужно обновлять осознанно: существующий volume может содержать старую установку. Не используйте `docker compose down -v` для обновления зависимостей — это затронет и том данных MySQL. Обновляйте только volumes зависимостей либо выполняйте корневой `npm ci` в нужном dev-контейнере.

При редактировании общих схем в контейнерной разработке также нужен watcher контрактов либо перезапуск приложения: контейнерный predev собирает пакет один раз.

Compose-конфигурация проверена. Сборка и запуск образов не подтверждены: Docker daemon в рабочем окружении недоступен. Контейнеры и БД в ходе переноса не запускались.

## 8. Разные машины и CI/CD

Клиент и сервер по-прежнему развёртываются независимо:

- Фронтенду достаточно содержимого `client/dist`: нужные схемы включены в браузерный бандл.
- Серверу нужны собранный код, runtime-зависимости и собранный пакет контрактов.
- Нельзя просто скопировать один `server/node_modules`: workspace-зависимости могут быть подняты в корень, а пакет подключён симлинком. Доставляйте нужную структуру либо устанавливайте упакованный/опубликованный пакет.
- CI получает репозиторий целиком, выполняет корневой `npm ci`, затем сборки и тесты.
- Публикация контрактов в npm пока не требуется; `private: true` сохраняется.

Версия пакета, PageConfig.schemaVersion и revision страницы — разные сущности. Общие исходники не гарантируют совместимость уже развёрнутых версий. Неизвестные поля в strict-схемах отклоняются, поэтому даже добавления требуют проверки совместимости.

## 9. Клиентский API страниц

Адрес навигации `/:locale/pages/:slug` использует slug пункта меню. `GET /api/pages/resolve/:slug` и `GET /api/pages/:id` возвращают одинаковый документ страницы в стандартном success-envelope: `data: { pageId, name, description, config, revision }`. Во втором маршруте `id` — ID страницы. Поиск по slug выполняет `PageService.getBySlug`: через существующий сервис меню находит видимый пункт с учётом всей цепочки родителей, затем вызывает тот же `PageService.get`, что и поиск по ID. Отсутствующий или недоступный пункт, отсутствие привязки и отсутствие страницы дают `404 COMMON.NOT_FOUND`. Оба API страниц сохраняют текущее требование системного администратора. `pageResolveParamsSchema` и `pageResponseSchema` экспортируются из `/pages`. Получение конфигурации по ID или slug в модуле меню отсутствует.

`client/src/shared/api/pages/index.ts` использует общий контракт:

- `pages.getPage(pageId, { signal })` — загрузка и проверка конфигурации, с проверкой совпадения ID ответа.
- `pages.getRows(pageId, params, { signal })` — загрузка строк, преобразование параметров в URL, проверка ответа и запрошенной пагинации.

`params` — объект с limit, offset и необязательным sort. Значения строк имеют тип unknown; их безопасное отображение остаётся задачей UI. Типы экспортированы в `page.types.ts`. React-компоненты и маршруты не добавлялись.

## 10. Проверки и дальнейшая работа

Перенос защищён существующими тестами API, тестами страниц/прав/движка и отдельным тестом shared-contracts. Он проверяет отсутствие удалённых файлов-мостов, CommonJS-импорты всех публичных entry points и отсутствие серверных/клиентских runtime-зависимостей в библиотеке.

Следующий продуктовый этап — React-экран страницы: загрузка конфига и строк, отрисовка колонок по config.list.columns, пагинация, состояния ошибки и загрузки. Пользователь хочет писать React сам. Права открытия страниц для обычных пользователей, capabilities и карточка записи остаются отдельными этапами — перенос контрактов их не реализует.
