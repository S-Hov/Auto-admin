# Страницы данных и единый JSON-протокол

Статус: принятая целевая архитектура, а не описание уже реализованных возможностей.
Дата фиксации: 22 октября 2026 года.

## 1. Задача

После настройки меню администратор настраивает страницы: какие данные получать, какие колонки показывать в списке, какие свойства открывать в карточке записи и как их оформлять. Система должна работать с существующей базой пользователя, учитывать права и не требовать написания отдельного React-компонента под каждую таблицу.

Источник описания страницы — JSON-конфигурация в служебной таблице. Её могут создавать визуальный редактор и в будущем ИИ-помощник. Оба используют один формат и одинаковые серверные проверки.

Главный принцип: **JSON — язык взаимодействия; Query Engine выполняет запросы к данным; сервисы выполняют системные операции; access-control проверяет разрешения.**

## 2. Что уже есть и что предстоит сделать

В проекте уже существуют schema-catalog, Query Engine с анализатором доступа и `QueryAuthorizer`, access-control и сервис меню. Меню поддерживает создание, изменение, перенос и удаление пунктов.

Пока нет самостоятельного модуля страниц, утверждённого runtime-контракта `PageConfig`, исполнителя страницы и общего диспетчера JSON-команд.

В существующем модуле query есть маршруты `/execute` и `/pipeline`. Этот документ не утверждает, что они уже заменены единым входом. Существующие API продолжают работать до отдельного этапа интеграции.

## 3. Страница не равна пункту меню

Пункт меню отвечает за навигацию: название, иконку, родителя, порядок и доступность самого пункта. Страница отвечает за содержимое: источники данных, список, карточку записи и настройки отображения.

Пункт меню получает nullable-поле `page_id`, которое в API называется `pageId`. Несколько пунктов могут ссылаться на одну страницу. У раздела-группы страница может отсутствовать. Существующие системные маршруты настроек продолжают работать: ссылку на страницу данных нельзя смешивать с маршрутом системного экрана.

Переименование или перенос пункта не меняет конфигурацию страницы. Удаление пункта не удаляет страницу и пользовательские данные. Первую версию удаления страницы выполняем отдельной операцией: если есть ссылки из меню, сервер отказывает и предлагает сначала убрать или изменить ссылки.

При сохранении меню через `POST /api/menu` поле `pageId` имеет три состояния:
положительный ID привязывает существующую страницу, `null` снимает привязку,
отсутствие поля сохраняет прежнюю привязку при обновлении и означает `null` при
создании. Это позволяет старым формам и перетаскиванию сохранять пункт без потери
ссылки. Сервер проверяет существование выбранной страницы в транзакции, чтение
управляемого и видимого меню возвращает `pageId`. Привязка не выдаёт права на страницу.

## 4. Хранение страниц

Целевая служебная таблица: `Auto_Admin__pages`.

| Поле | Назначение |
| --- | --- |
| `id` | Постоянный ID страницы; в контракте страницы — `pageId` |
| `name` | Название страницы |
| `description` | Необязательное описание |
| `config` | JSON-конфигурация по контракту `PageConfig` |
| `revision` | Целое положительное число, версия сохранения документа |
| `created_at`, `updated_at` | Время создания и изменения |
| `created_by`, `updated_by` | Кто создал и последним изменил страницу |

Типы ID и внешних ключей должны совпадать с существующими служебными таблицами. Физический тип JSON и особенности SQL определяет адаптер СУБД; сервис не должен зависеть от MySQL-синтаксиса.

Права не хранятся внутри `config`. Аудит создания, изменения и удаления страниц выполняется в той же транзакции, что и изменение. Храним страницу целиком, а не пытаемся в первой версии редактировать произвольные JSON-пути на стороне базы.

### Две разные версии

- `config.schemaVersion` — версия формата конфигурации. Меняется, когда меняется сам контракт.
- `revision` — версия конкретного документа. Увеличивается при каждом успешном изменении.

При сохранении клиент отправляет ожидаемую `revision`. Сервер атомарно проверяет её и обновляет документ с увеличением версии. При несовпадении возвращает конфликт, а не перезаписывает чужую работу. Проверка не должна состоять из отдельного незащищённого чтения и последующей безусловной записи.

## 5. Состав PageConfig

На первом этапе определяем строгую runtime-схему конфигурации и выводим из неё TypeScript-типы. Одна декларация типа не проверяет JSON, полученный от клиента или из БД. Неизвестную версию формата нельзя молча интерпретировать как текущую.

В конфигурацию входят следующие разделы.

### 5.1. Источники данных

Каждый источник имеет стабильный ID и описание запроса: основную таблицу, выбранные поля, связи и постоянные ограничения. Для первой версии достаточно одного источника списка и чтения одной записи из той же основной таблицы.

Описание должно ссылаться на ресурсы и поля каталога. Предпочтительны стабильные ID каталога, разрешаемые сервером в имена для Query Engine. Если контракт на первом этапе использует имена, это нужно явно зафиксировать; переименование тогда требует проверки конфигурации, а не угадывания новой таблицы.

Формат источника преобразуется в существующий JSON-контракт Query Engine. Не создаём второй SQL-компилятор внутри модуля страниц. Нельзя сохранять произвольный SQL или исполняемые выражения.

### 5.2. Список записей

- Стабильные ID колонок, отличные от пользовательских подписей.
- Привязка каждой колонки к конкретному полю источника.
- Подпись, порядок и видимость.
- Способ отображения: текст, число, дата, логическое значение, изображение, ссылка и другие зарегистрированные варианты.
- Разрешённые пользователю сортировки и фильтры.
- Начальная сортировка и параметры пагинации.

Тип значения и его представление — разные вещи. Например, строка может отображаться как текст или изображение. Форматирование не меняет сохранённый тип данных.

### 5.3. Карточка записи

Карточка открывается по выбору строки и показывает дополнительные поля, объединённые в группы. Не загружаем все подробности всех записей заранее.

Отдельные связанные списки, например товары заказа, получают собственные источники и пагинацию на следующих этапах. Нельзя переносить произвольную связь один-ко-многим в основной JOIN: это может размножить строки основной сущности и испортить пагинацию.

### 5.4. Идентификация записи

Идентификатор записи — не обязательно поле `id`. Используем полный первичный либо другой подходящий уникальный ключ, в том числе составной. Внутренний ключ строки отделён от видимых колонок и не обязан показываться в таблице.

Ключ, переданный клиентом, — адрес записи, а не доказательство доступа. Сервер проверяет формат, соответствие источнику и разрешения. Не отправляем скрытые секретные поля только ради идентификации строки. Если подходящий ключ нельзя безопасно использовать при текущих правах, карточка и операции над отдельной строкой недоступны либо требуют отдельного безопасного механизма идентификации.

Если у таблицы нет подходящего ключа, можно поддержать просмотр списка, но нельзя обещать надёжное редактирование или удаление конкретной строки.

### 5.5. Действия

Конфигурация может описывать желаемые действия интерфейса. Это не выдаёт пользователю права на их выполнение. Возможности создания, изменения и удаления появятся после первого завершённого сценария чтения.

## 6. Загрузка страницы и данных

Для выбора страницы в редакторе меню существует административный
`GET /api/pages?q=...&limit=25&offset=0`. Поиск `q` — подстрока названия (до 100
символов, внешние пробелы убираются); `%` и `_` не являются масками. Размер выдачи
по умолчанию 25, максимум 100; `offset` от 0 до 100000. Сортировка — название,
затем ID. Ответ в общем envelope содержит `data.items: { pageId, name }[]` и
`data.pagination: { limit, offset, hasMore }`, без конфигураций страниц и общего
`COUNT`. Для продолжения клиент увеличивает offset на limit, пока hasMore=true.
Эндпоинт доступен только системному администратору; пустой список — успешный ответ.

Обычное открытие страницы работает так:

1. Клиент передаёт `pageId` и получает доступную текущему пользователю конфигурацию и возможности интерфейса.
2. React собирает экран из зарегистрированных компонентов.
3. Клиент запрашивает источник, передавая `pageId`, ID источника, `revision`, выбранные фильтры, сортировку и пагинацию.
4. Сервер загружает сохранённую конфигурацию. Клиентские параметры могут менять только предусмотренные в ней настройки.
5. Сервер формирует канонический запрос Query Engine и выполняет его от имени текущего пользователя с актуальной проверкой прав.
6. Клиент получает строки, возможности и сведения о пагинации.
7. При открытии карточки выполняется отдельный запрос по ключу записи.

Клиент не присылает произвольную замену источника или обязательных условий сохранённой страницы. Пользовательские фильтры добавляются к обязательным ограничениям, а не заменяют их. Неизвестные источники, колонки сортировки и фильтры отклоняются.

Если `revision` страницы изменилась, сервер сообщает конфликт конфигурации. Клиент повторно загружает страницу, а не отображает новые данные по старому описанию.

Сохраняем общий API envelope проекта. В его `data` логически разделяем:

- `rows` — записи;
- `capabilities` — доступные действия;
- `pagination` — размер страницы, позицию и признак наличия продолжения;
- `pageRevision` — версию использованной конфигурации.

Точные поля ответа утверждаются runtime-схемой на этапе реализации. Полное количество записей не обязательно вычислять для каждого запроса: дорогой `COUNT` должен быть отдельным осознанным решением.

## 7. Права и адаптация интерфейса

### 7.1. Независимые уровни

1. Доступ к пункту меню.
2. Доступ к самой странице.
3. Права на таблицы, поля и действия с данными.

Отсутствие пункта меню не запрещает работу с таблицей, если пользователь имеет соответствующие права. Наличие пункта и разрешение открыть страницу не разрешают читать её данные автоматически.

Управление конфигурациями страниц в первой версии доступно только системному администратору. Для открытия страниц предусматриваем отдельную политику: явные разрешения ролям и пользовательские переопределения с использованием принятой в access-control модели наследования. Это новые права на страницы, а не уже существующие права меню. Физическую схему этих правил нужно согласовать с текущим access-control до создания миграций; не прятать её в JSON страницы.

Пока такой модели открытия нет, первый вертикальный сценарий допускается только для системного администратора. Нельзя временно разрешить всем открытие произвольной страницы и оставить это неявным правилом.

### 7.2. Возможности интерфейса

Сервер возвращает разрешённые действия на уровне ресурсов и полей. Например, поле можно читать, но нельзя изменять. Клиент показывает его как текст или read-only поле, а не предлагает заведомо запрещённую операцию.

`capabilities` не являются разрешительным токеном. Пользователь определяется серверной сессией. Перед каждой операцией access-control заново проверяет действующие права; присланным клиентом `userId`, роли или возможностям доверять нельзя.

Сначала достаточно прав на ресурс и поле. Будущие ограничения на отдельные записи потребуют дополнительных проверок: общая возможность редактирования таблицы не должна трактоваться как разрешение менять любую строку.

### 7.3. Адаптация общей конфигурации

Администратор создаёт один исходный конфиг. Сервер строит его доступное пользователю представление без изменения оригинала:

- необязательные запрещённые колонки, поля карточки, действия и элементы управления исключаются;
- запрещённые поля не запрашиваются и не попадают в ответ;
- если недоступна основная таблица или обязательное поле связи, фильтра либо другое необходимое условие, источник становится недоступен;
- нельзя убирать обязательное ограничение, чтобы запрос «хоть как-нибудь выполнился»;
- нельзя выполнять запрос с правами администратора и просто прятать часть значений на клиенте.

Адаптацию выполняем до исполнения запроса, а затем обычный авторизатор Query Engine проверяет итоговый запрос. Не нужно сначала выполнять заведомо запрещённый запрос и ловить отказ ради обрезания результата.

Состояния «нет записей», «нет доступа», «конфигурация устарела» и «источник сломан» должны различаться. Не заменяем отказ пустым массивом. Не раскрываем обычному пользователю SQL, секретные значения или внутренние детали недоступных ресурсов.

Отдельные конфигурации интерфейса для ролей и пользователей не входят в первый этап. Их можно добавить поверх этой модели, но они также не будут выдавать права.

## 8. Единый JSON-вход

Цель — один общий endpoint для операций админки после установки, а не замена всех HTTP-механизмов приложения. Установка, сессии, загрузка файлов и другие специальные сценарии не обязаны превращаться в команды Query Engine.

Целевой вход: `POST /api/commands/execute`. Название фиксирует направление реализации, но endpoint ещё не существует. Формат верхнего уровня содержит версию протокола и явный вид команды. Сервер выбирает обработчик из закрытого реестра, а не из имени класса или функции, присланного клиентом.

| Вид | Примеры | Исполнитель |
| --- | --- | --- |
| `query` | Разрешённый запрос к пользовательской таблице | Query Engine |
| `page` | Загрузка конфигурации, списка, карточки записи | Сервис страниц, затем Query Engine для данных |
| `system` | Сохранение страницы, перенос пункта меню, изменение прав | Соответствующий системный сервис |

Для каждого вида и действия нужна отдельная строгая runtime-схема. Общий контроллер отвечает за HTTP и передачу текущего пользователя; диспетчер маршрутизирует команду; сервис выполняет бизнес-операцию.

Конкретный JSON-синтаксис команд необходимо утвердить перед реализацией диспетчера. Протокол не должен изображать существующие вызовы `UnifiedQuery`: его внешний envelope и контракт самого движка — разные уровни.

### Почему служебные таблицы нельзя открыть обычному CRUD

Произвольный UPDATE служебной таблицы может обойти бизнес-правила: создать цикл в меню, выдать права в обход политики, подменить версию конфигурации или не записать аудит.

Поэтому общедоступный Query Engine по умолчанию закрывает служебные ресурсы. Команды к системе вызывают существующие сервисы, которые соблюдают свои проверки, транзакции и аудит. Даже системному администратору не предоставляется обход этих правил через произвольный публичный CRUD служебных таблиц.

Внутренняя реализация репозитория системного сервиса может использовать SQL или движок через специально ограниченный внутренний адаптер. Это не расширяет права публичного query-входа.

Все публичные входы, включая старые query-маршруты, обязаны соблюдать эти ограничения. Проверка только в новом диспетчере не защищает обход через старый endpoint.

Не переписываем готовые сервисы ради единого URL. Диспетчер подключаем к ним как новый вход. Объединение ответов нескольких команд не означает общую транзакцию: массовые и составные операции требуют отдельного контракта, ограничений и явной семантики. В первой версии общий диспетчер выполняет одну команду за запрос.

## 9. Ограничения и безопасность

- Runtime-валидация входящих команд, сохранённых конфигураций и ответов API.
- Проверка источников и полей по актуальному schema-catalog.
- Ограничения размера JSON, вложенности, числа источников, JOIN и выбранных полей.
- Обязательная серверная пагинация и предельный размер страницы.
- Стабильная сортировка с уникальным ключом как дополнительным критерием, когда такой ключ доступен.
- Лимиты времени выполнения и объёма результата на стороне движка и адаптера.
- Параметризованные значения; идентификаторы таблиц и полей — только после проверки каталога.
- Текущие механизмы аутентификации, защиты изменяющих запросов и rate limiting сохраняются для общего входа.
- Запрет произвольного JavaScript, SQL и HTML в конфигурации.
- Только зарегистрированные типы отображения. Неизвестный renderer даёт ошибку конфигурации.
- Проверка URL изображений и ссылок. SVG не вставляется как произвольная непроверенная HTML-разметка. Загрузка внешних изображений также раскрывает внешний адрес и сетевой запрос: это отдельная настройка, а не безусловно безопасная возможность.
- Обязательные условия источника не редактируются обычным запросом данных.
- Изменения конфигураций и прав фиксируются в аудите без секретных значений пользовательских записей.

Кэширование конфигураций можно добавить по `pageId/revision`. Пользовательские представления и возможности нельзя кэшировать только по `pageId`: они зависят от пользователя и актуальности прав. На первом этапе лучше обойтись без отдельного кэша разрешений, чем добавить кэш без механизма инвалидирования. Кэш никогда не заменяет проверку операции.

## 10. Изменение структуры базы

Сохранённая страница может устареть: поле удалили, таблицу переименовали, тип изменился. При сохранении проверяем конфиг по каталогу; при выполнении повторно проверяем актуальность используемых ресурсов.

При несовместимости сервер возвращает структурированную ошибку. Администратор получает диагностику для исправления страницы, обычный пользователь — безопасное сообщение о недоступности источника. Автоматически подставлять похожие поля, ослаблять ограничения или выполнять частично изменённый запрос нельзя.

## 11. Будущий ИИ-помощник

ИИ получает доступный пользователю каталог, разрешённые действия и описание JSON-протокола. Он генерирует те же запросы и системные команды, что и интерфейс, и отправляет их через тот же публичный вход.

Переданный модели список прав помогает построить корректную команду, но не является доказательством разрешения. Сервер не доверяет ни модели, ни клиенту. Системные и пользовательские данные не должны позволять модели подменять серверную политику.

Чтение и изменение — разные уровни риска. Перед удалением и другими опасными изменениями пользователь должен явно подтвердить конкретную операцию. Поле `confirmed: true` в JSON, которое ИИ может сам написать, подтверждением не считается. Механизм подтверждений связывает согласие пользователя с точным действием на сервере; его реализуем до включения автономных изменений ИИ.

## 12. Порядок реализации

### Этап 1. Контракт и хранение

1. Утвердить минимальную runtime-схему `PageConfig` и типы из неё.
2. Реализовать таблицу страниц, связь меню со страницей и необходимые миграции с учётом адаптеров.
3. Создать модуль страниц: репозиторий, сервис, валидация и API. Все действия пока доступны только системному администратору.
4. Добавить аудит и проверку `revision` при сохранении.

Результат: администратор может сохранить и получить валидную конфигурацию, привязать её к пункту меню. Защита служебных таблиц не ослабляется.

### Этап 2. Первый рабочий экран

1. Одна основная таблица, выбранные колонки, без произвольных JOIN.
2. Получение данных через Query Engine с действующим авторизатором.
3. Таблица с серверной пагинацией и разрешённой сортировкой.
4. Отдельная загрузка дополнительных данных выбранной записи по надёжному ключу.
5. Явные состояния загрузки, пустого результата, ошибки, недоступности и устаревшей конфигурации.

Результат: реальный пользовательский сценарий от пункта меню до просмотра записи. Полный визуальный конструктор и общий диспетчер не должны задерживать этот результат.

### Этап 3. Открытие страниц другим пользователям

1. Реализовать явные права на страницы, согласованные с текущей моделью access-control.
2. Возвращать доступную конфигурацию и `capabilities`.
3. Убирать необязательные недоступные элементы до сборки запроса и отказывать при недоступности обязательных.
4. Проверять изменения прав между загрузкой экрана и выполнением действия.

Результат: одна настроенная страница безопасно работает для пользователей с разными правами.

### Этап 4. Общий JSON-вход

1. Утвердить versioned-envelope и закрытый реестр команд.
2. Подключить Query Engine, сервис страниц и существующие системные сервисы.
3. Переводить клиентские вызовы постепенно, не дублируя бизнес-логику.
4. Старые входы либо сохраняют все проверки, либо удаляются после миграции клиентов.

Результат: интерфейс и будущий ИИ используют единый протокол без прямого CRUD служебных таблиц.

### Этап 5. Развитие

Редактор колонок и групп карточки, автоматические и ручные связи, отдельные связанные списки, расширенные форматы отображения, операции изменения данных и только затем специальные варианты интерфейса ролей и пользователей.

## 13. Проверки перед завершением первого рабочего этапа

- Конфигурация сохраняется, открывается после перезапуска и валидируется на обеих границах API.
- Конкурентное сохранение устаревшей `revision` не затирает новое состояние.
- Данные читаются через Query Engine; невозможно заменить источник или снять обязательный фильтр параметрами запроса.
- Сортировка и фильтры не принимают произвольные поля, а пагинация ограничена сервером.
- Карточка корректно адресует запись, в том числе составным ключом; без ключа не предлагает небезопасные действия.
- Удаление пункта меню не удаляет страницу или пользовательские данные.
- Произвольный запрос к служебным таблицам не обходит сервисы.
- После включения пользовательского доступа: скрытые поля отсутствуют и в данных, и в доступной конфигурации; изменение прав действует на следующую операцию.
- Необходимая недоступная связь не исчезает молча, и отказ не выдаётся за пустой список.
- Поломка схемы БД даёт понятное состояние, а не непроверенный fallback.

## 14. Что пока не делаем

Не строим сразу универсальный dashboard-конструктор, произвольные скрипты, индивидуальные конфигурации каждого пользователя, универсальные пакетные транзакции и автономную запись данных ИИ.

Ближайшая цель — законченная страница списка и карточка записи на существующем Query Engine. Расширения добавляются через версионируемый контракт, а не через отказ от проверок ради универсальности.
