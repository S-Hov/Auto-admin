# Страницы: поиск, фильтры и итоговые показатели

Дата фиксации: 17 ноября 2026 года.

Это продолжение `pages-and-json-protocol-architecture.md`. Документ фиксирует
согласованную архитектуру и точку остановки разработки. Примеры будущих API
и разделов конфига — проект решения, а не уже реализованный контракт.

## 1. Точка остановки: что готово

В интерфейсе PageTable добавлены макетные карточки итогов, поиск и селекторы.
Эти блоки пока не связаны с поисковыми условиями и агрегатами на сервере.
Существующая загрузка строк, сортировка и пагинация работают отдельно.

Для поиска уже написаны:

- `packages/contracts/src/pages/page-search.schema.ts`: строгие схемы
  pageSearchFieldSchema/pageSearchSchema, типы, запрет дублирования fieldId,
  от 1 до 10 настроек поиска;
- необязательный `search` в pageConfigSchema и экспорт схем из пакета;
- `server/src/core/schema-catalog/types/field-type-category.ts`: общие
  классификаторы текстовых и числовых типов без экспорта изменяемых Set;
- `server/src/modules/pages/schema/page-search-compatibility.ts`:
  проверка совместимости режима поиска и типа колонки;
- обход search.fields в validatePageConfigAgainstCatalog: существование,
  принадлежность таблице и совместимость; обход расположен до раннего
  выхода при отсутствии recordKey;
- RU/EN-переводы PAGE.SEARCH_INCOMPATIBLE.

### Незавершённый пункт прямо сейчас

В `packages/contracts/src/common/error-codes.ts` ещё нет записи:

```typescript
PAGE_SEARCH_INCOMPATIBLE: 'PAGE.SEARCH_INCOMPATIBLE',
```

Валидатор уже обращается к этой константе. Проверка `npm run typecheck`
17 ноября завершилась ошибкой TS2551 именно по этой причине.
Первое действие при продолжении: добавить константу и повторить проверку.

Поиск пока не подключён к запросам строк и редактору страницы.
Проверка настроек при сохранении — это ещё не выполнение поиска.

## 2. Одна конфигурация, несколько независимых загрузок

Настройки остаются в одном PageConfig в существующей записи страницы.
Отдельные таблицы конфигов поиска, фильтров и карточек сейчас не нужны:
эти части редактируются как один документ и используют общую revision.

При этом Zod-схемы, компоненты и серверные построители разделяем по задачам.
Один JSON-документ не означает один огромный файл реализации.

Разделы конфигурации:

| Раздел | Содержимое |
| --- | --- |
| source, fields, list, detail | Уже существующие источник, поля и представления |
| search | Поля и способы поиска; схема уже добавлена |
| filters | Будущие селекторы и другие структурированные фильтры |
| summaries | Будущие определения итоговых карточек |

Последние два названия — рабочие до проектирования их строгих схем.
Если раздела нет, соответствующая возможность отключена.
Значения, введённые пользователем, в сохранённый конфиг не записываются.

После получения конфигурации независимо загружаем:

1. Строки таблицы.
2. Все итоговые показатели страницы одним запросом.
3. Динамические варианты селекторов, только если такие фильтры настроены.

Не делаем HTTP-запрос на каждую карточку и каждый статический вариант фильтра.
У блоков собственные состояния загрузки, ошибки и повторного запроса.
Ошибка итогов не должна блокировать уже загруженную таблицу.

Раздельные запросы позволяют постепенно показывать интерфейс, но сами по себе
не уменьшают нагрузку: параллельные тяжёлые запросы могут её увеличить.
Для нагрузки нужны ограничения, индексы, отмена устаревших запросов,
объединение совместимых агрегатов и измерения на реальных данных.
Отмена fetch не гарантирует остановку уже выполняющегося SQL.

## 3. Поиск: сохранённые настройки

У каждой настройки есть fieldId из schema-catalog и mode:

```json
{
  "search": {
    "fields": [
      { "fieldId": 101, "mode": "startsWith" },
      { "fieldId": 102, "mode": "contains" },
      { "fieldId": 103, "mode": "exact" }
    ]
  }
}
```

Здесь 101 может означать имя, 102 — почту, 103 — числовой ID.
Это идентификаторы колонок каталога, а не значения строк.

| Режим | Значение |
| --- | --- |
| exact | Полное совпадение значения |
| startsWith | Значение начинается с введённого текста |
| contains | Значение содержит введённый текст |

Условия по поисковым полям объединяются через ИЛИ. В первой версии вся
введённая строка считается одним значением, без разбора на слова и языка запросов.
Пустой после trim поиск не добавляет поисковых условий.

Поисковая колонка не обязана присутствовать среди отображаемых config.fields.
Например, можно искать по артикулу, не показывая его в таблице.
Но колонка обязана принадлежать source.resourceId, существовать в каталоге
и быть разрешена пользователю при выполнении запроса.

Текстовые типы допускают все три режима, числовые — только exact.
Даты, bool/boolean, JSON, бинарные и неизвестные типы пока не включаем;
для дат и логических значений позже появятся специализированные фильтры.
MySQL tinyint(1) сейчас попадает в числовую классификацию — отдельного
исключения для него текущая функция поиска не делает.

## 4. Поиск: параметры и построение запроса

Клиент отправляет введённый текст, но не выбирает заново колонки и операторы.
Например, внутренние параметры списка после расширения контракта:

```json
{ "search": "Иван", "limit": 25, "offset": 0 }
```

Для текущего GET /api/pages/:id/rows это параметры URL. Нужно согласованно
расширить pageRowsQuerySchema, pageRowsHttpQuerySchema и клиентскую сериализацию.
Начальный согласуемый лимит строки — 200 символов после trim; сервер обязан
ограничивать также исходную длину HTTP-параметра, до преобразования.

Сервер берёт разрешённые поля из сохранённого PageConfig и строит WhereClause
существующего Query Engine. Не создаём второй SQL-компилятор внутри pages.
Рекомендуемая отдельная чистая функция: build-page-search-condition.ts.
Она проверяет аргументы/каталог и возвращает условие, но не выполняет SQL.

Важные правила реализации:

- Для числового exact нужен строгий разбор всей строки. Нельзя использовать
  parseInt('20abc') или Number('') как допустимый ввод.
- BIGINT/DECIMAL нельзя бездумно преобразовывать в JS number: возможна потеря
  точности. Представление и допустимость значений согласуются с Query Engine
  и драйвером, а не обходятся небезопасным приведением типа.
- Если ввод «Иван» нельзя применить к числовому полю, пропускаем только эту
  ветку ИЛИ; текстовые ветки продолжают работать.
- Если ввод непустой, но ни одной применимой ветки не осталось, результат
  должен быть пустым. Нельзя просто удалить WHERE и показать всю таблицу.
  Способ представления этого случая в Query Engine нужно определить явно.
- Для contains/startsWith символы SQL LIKE `%`, `_` и escape-символ должны
  трактоваться как обычный пользовательский текст. Проверяем возможности
  компилятора и при необходимости добавляем безопасную поддержку экранирования.
  Параметризация защищает от SQL-инъекции, но сама не отменяет wildcard-семантику.
- exact означает равенство по правилам типа и collation базы, а не обязательно
  побайтовое совпадение с учётом регистра. В первой версии отдельный переключатель
  регистра не обещаем.
- Значения передаются параметрами, имена разрешаются по каталогу.

Если непустой search передан странице без настроенного поиска, сервер
возвращает ошибку валидации, а не молча игнорирует параметр.

Итоговая логика: постоянные условия источника И поисковая группа И фильтры
И ограничения доступа. Внутри поисковой группы — ИЛИ по настроенным полям.

## 5. Селекторы и другие фильтры

Фильтр получает стабильный ID, подпись, привязку к полю каталога и тип.
ID фильтра не равен его пользовательской подписи и не является произвольным
SQL-идентификатором. Клиент отправляет ID фильтра и выбранные значения.

Источники вариантов:

- Статические: значения/подписи сохраняются в конфиге. Подходят для небольшого
  заранее известного списка статусов. Дополнительный запрос не нужен.
- Динамические: варианты загружаются из разрешённого источника. Например,
  ID и имя менеджера. Нужны лимит, поиск по вариантам, пагинация и проверка прав.

Не скачиваем все уникальные значения большой таблицы ради select.
ENUM можно использовать как подсказку редактору, но его наличие не заменяет
настройку интерфейса и проверку прав. Данные каталога ENUM пока специально
для этого не расширены.

Первая версия — независимые селекторы, без каскадного обновления вариантов
при изменении соседнего фильтра. Сам запрос вариантов всё равно учитывает права.
Разные фильтры объединяются через И, несколько выбранных значений одного
фильтра — через IN/ИЛИ. Не выбранный фильтр условий не добавляет.
Пустая строка, отсутствие значения и NULL не должны смешиваться.

## 6. Итоговые показатели

Карточка содержит стабильный ID, подпись, агрегат, при необходимости fieldId,
формат отображения и область расчёта. Для COUNT строк fieldId не обязателен;
COUNT значений поля и SUM имеют другую семантику.

Начальная цель — количество строк и сумма числового поля. MIN/MAX/AVG добавлять
после базового контракта и реализации в Query Engine, не через произвольный SQL.

Две области:

- «Вся доступная выборка»: постоянные условия источника и права, без текущего
  пользовательского поиска и фильтров.
- «С учётом фильтров»: те же условия плюс текущий поиск и фильтры.

Агрегаты считаются по всем подходящим строкам, а не по загруженным 25 записям.
Пагинация и сортировка списка не должны менять результат карточек.
Нельзя загружать все строки в браузер для расчёта суммы.

У Query Engine пока нет подтверждённого контракта агрегатов: перед итогами
нужно расширить runtime-схемы, типы, анализатор доступа и компилятор.
Права проверяются и на агрегируемое поле, и на поля условий/группировок.
Служебные таблицы остаются защищены существующей политикой.

Ноль, NULL, ошибка и отсутствие доступа — разные состояния. Не выдаём ноль
вместо запрета. Для списка без совпадений COUNT равен 0; семантику SUM по
пустой выборке (NULL или отображаемое 0) фиксируем в контракте, не угадываем в UI.
При будущих JOIN учитываем размножение строк: COUNT строк соединения не всегда
равен количеству заказов, а SUM может завыситься. Первая версия — один источник.

Точный общий COUNT нужен не каждой странице: существующий hasMore можно
сохранить. Макетное «1–15 из 20» нельзя оставлять как реальные данные.
Если COUNT ещё не получен, показываем диапазон без выдуманного общего числа.

## 7. Разделение ответственности и права

На клиенте нужен небольшой сборщик состояния: поиск, ID фильтров и значения,
сортировка, лимит, смещение. Полноценный Query Engine и SQL-знания ему не нужны.

На сервере:

1. Runtime-валидация входа.
2. Загрузка конфигурации и проверка доступа к странице.
3. Разрешение полей/режимов по конфигу и каталогу.
4. Построение JSON-запроса Query Engine.
5. Обязательная проверка Access Control и исполнение.
6. Преобразование результата в публичный контракт.

Права проверяются и для скрытых полей в WHERE. Нельзя скрыть запрещённую колонку
в SELECT, но позволить узнавать её значения через поиск, варианты select или итоги.
Настройка страницы не предоставляет право на данные. Общий JSON API для AI
остаётся отдельным сценарием и также всегда проверяется сервером.

Кеш результатов, если понадобится, учитывает пользователя/область доступа,
изменения прав, revision страницы, нормализованные условия и срок жизни данных.
Один глобальный кеш по pageId небезопасен. На первом этапе кеш результатов
не нужен; имеющийся кеш метаданных — другая задача.

## 8. Поведение клиента и согласованность

- Изменение поиска/фильтров сбрасывает offset в 0.
- Для ввода поиска — задержка примерно 300 мс и отмена устаревшего fetch.
- Запоздавший ответ не заменяет данные для нового состояния запроса.
- Итоги и строки используют одинаково нормализованные условия.
- Динамические варианты не перезагружаются при каждой смене страницы таблицы.
- Ответы блоков содержат revision, чтобы обнаружить изменение конфига
  между запросами и предложить перезагрузить страницу.
- Совпадение revision не означает один снимок данных БД: независимые запросы
  могут видеть изменения, сделанные между ними. Строгий единый снимок требует
  отдельного серверного протокола; для первой версии его не обещаем.
- При обновлении существующего конфига редактор обязан сохранять новые разделы.
  Нужно проверить build-page-config.ts/edit-page-config.ts: реконструкция только
  старых свойств не должна незаметно удалять search, затем filters/summaries.

## 9. Порядок продолжения

1. Добавить пропущенную константу PAGE_SEARCH_INCOMPATIBLE и проверить TypeScript.
2. Проверить схемы и валидацию поиска: чужое/удалённое поле, неподходящий режим,
   отсутствие search, отсутствие recordKey, допустимое скрытое поле.
3. Расширить внутренние и HTTP-параметры строк и клиентский API полем search.
4. Спроектировать строгую конвертацию чисел и экранирование LIKE; написать
   чистый построитель поискового условия и подключить к buildPageListQuery.
5. Проверить Access Control на полях поиска, затем подключить ввод PageTable.
6. Добавить настройку поисковых полей/режимов в редактор страницы и сохранение.
7. Реализовать один статический фильтр, затем поддержку агрегатов и итогов.
8. Динамические источники вариантов, расширенные фильтры и оптимизация по замерам.

Тесты писать по этим границам: контракты, построитель условий, права, HTTP/API,
пользовательские переходы. Отдельно проверить пустой поиск, `%`/`_`, неверный
числовой ввод, BIGINT/DECIMAL, смену фильтра на последней странице и гонку ответов.

Режим работы при продолжении: разработчик пишет код, помощник проверяет
и объясняет следующий этап. Этот документ не означает, что весь план уже реализован.
